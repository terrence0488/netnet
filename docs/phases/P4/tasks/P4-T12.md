# P4-T12: An agent's error names the tool's own fields

Status: todo
Depends on: none
Parallel-safe: yes

## Goal

When a tool call fails, every field its error names, in the message as well as in `fields`, is a
parameter of that tool as the agent called it, so even a weak model can correct itself (J6, M12).

## Context

- P3's test report, issue 1 (Low): `record_values` with a `holding_id` naming no holding answers
  the message `values[1].holdingId: There is no holding "hld_…" in this account.`, while `fields`
  has `values[1].holding_id` and the tool's schema only `holding_id`. A weak model may then send
  `holdingId`, which the tool refuses as "not a field here". The fault predates P3.
- `apps/api/src/mcp/errors.ts` renames the Ledger's camelCase paths in `fields` to the tool's
  parameters (`renamePaths`, with per-tool `renames` such as `access` → `access_answer`), but the
  top-level `message` is the Ledger's own text and keeps its paths.
- The REST API keeps camelCase in both, as its contract is camelCase (CONVENTIONS §4). Only the
  MCP mapping changes.
- Architecture §7.4: errors are returned in `structuredContent` and as the same JSON in the text
  content; both carry the corrected message.

## Interface contract

- The MCP error mapping applies the same renames to every field path that appears in `message`
  (and in any per-field message that quotes another path), so `message` and `fields` agree.
- No change to error codes, HTTP mapping, REST bodies or tool schemas.
