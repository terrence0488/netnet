# P4-T12: An agent's error names the tool's own fields

Status: todo
Depends on: none
Parallel-safe: yes

## Goal

When a tool call fails, every field its error names, in the message as well as in `fields`, is a
parameter of that tool as the agent called it, so even a weak model can correct itself (J6, M12).

## Context

- P3's test report, issue 1 (Low): `record_values` with a `holding_id` naming no holding answers
  the message `values[1].holdingId: There is no holding "hld_…" in this account.`, while `fields`
  has `values[1].holding_id` and the tool's schema only `holding_id`. A weak model may then send
  `holdingId`, which the tool refuses as "not a field here". The fault predates P3.
- `apps/api/src/mcp/errors.ts` renames the Ledger's camelCase paths in `fields` to the tool's
  parameters (`renamePaths`, with per-tool `renames` such as `access` → `access_answer`), but the
  top-level `message` is the Ledger's own text and keeps its paths.
- The REST API keeps camelCase in both, as its contract is camelCase (CONVENTIONS §4). Only the
  MCP mapping changes.
- Architecture §7.4: errors are returned in `structuredContent` and as the same JSON in the text
  content; both carry the corrected message.

## Interface contract

- The MCP error mapping applies the same renames to every field path that appears in `message`
  (and in any per-field message that quotes another path), so `message` and `fields` agree.
- No change to error codes, HTTP mapping, REST bodies or tool schemas.

## Files in scope

- `apps/api/src/mcp/errors.ts` and its tests
- `apps/api/test/mcp/**`

## Done criteria

- [ ] P3's case answers `values[1].holding_id: There is no holding "hld_…" in this account.`
- [ ] For every write tool, every path named in a validation or not-found error's `message` and
      `fields` is a parameter in that tool's `inputSchema` (a registry test walks every tool and
      its error cases)
- [ ] REST errors are unchanged
- [ ] Tests written and passing: the failing case first, then the registry test
- [ ] Follows CONVENTIONS.md

## Report (filled by engineer)
Files changed:
- `apps/api/src/mcp/errors.ts`: new `renameText`, which renames every Ledger path a message
  names with the tool's renames: a path with an index or a dot (`values[1].holdingId`), a
  camelCase name further on (`leave fxRate out`, `with allowDuplicate`, `with deleteTag and
  mergeInto`), bare or in backticks, and a field's own name where the message lists it
  (`access: …`). Plain words stay even when one equals a field's name ("the universal type"), and
  so does text in double quotes (ids, answers, codes, pack questions, quoted as given).
  `toMcpError` applies it to `message` and to each field's message, so they agree with `fields`;
  the `AppError` itself is not changed. Only camelCase segments are snake_cased now, so an id or a
  code in a path is never rewritten. A rename may name a whole path as well as a segment.
  `renames: null` renames nothing (see Deviations).
- `apps/api/src/mcp/errors.test.ts`: 8 new tests (the null case; message and `fields` renamed
  alike, with the `(4 problems; see fields.)` tail, and the error left camelCase; the duplicate's
  hint; `renameText` at the start, with indexes and nested segments, a whole-path rename, paths
  further on and in backticks, a field's own name only where listed, quoted values, ids, codes,
  names and plain words untouched)
- `apps/api/src/mcp/server.ts`: `callTool` passes `renames: null` until the tool's input schema
  has parsed the arguments, then `tool.renames` for the Ledger's errors
- `apps/api/src/mcp/tools/create-holding.ts`: `renames` gains `'opening.currency': 'currency'`
- `apps/api/src/mcp/tool.ts`: `renames`' doc says it maps paths or segments
- `apps/api/test/mcp/tools-writes.test.ts`: 4 new tests: P3's case (exact message and `fields`),
  a first value with no rate names `currency`, and a misspelt field named as sent for
  `create_holding` (`access`) and `record_values` (`values[0].fxRate`)
- `apps/api/test/mcp/error-names.test.ts` (new): the registry test. 60 failing calls across the
  ten write tools (each validation, range, currency and not-found error the Ledger raises through
  them, schema refusals, the duplicate's hint, and a misspelt field per tool). Each checks that
  `fields` names exactly the expected paths, that the message lists them as `fields` has them,
  and that every path in `fields`, the message and each field's message is a parameter of the
  `inputSchema` `tools/list` advertises, as it is or within the item a field belongs to (`… leave
  fx_rate out` under `values[0].fx_rate`), or of a tool the message points to (`upsert_tag`'s
  clash names `delete_tag` and `merge_into`); a misspelt key must be named as sent. A registry
  check fails unless every write tool has cases, a not-found, a validation error and a misspelt
  field among them; another checks every rename lands on a parameter. Four REST cases show the
  same Ledger errors keep camelCase in message and `fields` (`fxRate`, `typeId` with
  `opening.fxRate`, `moveTo`, `deleteTag`/`mergeInto`) beside the MCP answer.

Deviations:
- Three files outside the brief's scope, no contract changed (error codes, HTTP mapping, REST
  bodies and tool schemas are as they were):
  - `server.ts`: an error from the tool's own input schema already names the arguments as the
    agent sent them, yet it went through the Ledger's renames. A key the tool does not have was
    renamed to the parameter it resembles (`fxRate` → `values[0].fx_rate: This is not a field
    here`, `access` → `access_answer: …`), in `fields` before this task; renaming the message as
    the brief asks would have spread that to the message. Only the Ledger's errors are renamed
    now, so a misspelt field is named as sent in both.
  - `create-holding.ts` and `tool.ts`: with no rate for a new holding's currency, the Ledger fails
    the opening value at `opening.currency`, which segment renames made `opening_value.currency`,
    not a parameter. A rename can now name a whole path, and `create_holding` maps it to
    `currency`.
- "Quoted inside it" is read as named inside it: double-quoted text in these messages is what the
  agent or the content gave, so it is never renamed; a path in backticks is.
Open issues:
- The liability message, `access_answer: A liability has no accessibility: … Leave access out.`,
  still says `access` in its last sentence: a bare word that is also an ordinary word cannot be
  renamed safely, so the mapping leaves it, and the registry test counts plain words as words.
  The entry's own name is right. Rewording the Ledger's sentence (for example "Leave it out.")
  would settle it but changes the REST message, so it is not done here.
- Read tools are outside this brief's criteria, and the registry test does not walk them. One
  wrong path seen there: `get_holding` with a bad `values_cursor` answers `values.cursor` (the
  Ledger's `values` page root plus `cursor`). The whole-path rename now allows
  `renames: { 'values.cursor': 'values_cursor' }` in `get-holding.ts`; extending the registry
  test to the read tools would find any other.
- REST has the same `opening.currency` path for a new holding's first value with no rate; its
  body has no `opening.currency` either. Unchanged here, as REST must be.
