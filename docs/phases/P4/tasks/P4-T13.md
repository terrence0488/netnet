# P4-T13: The security review before launch

Status: todo
Depends on: P4-T1, P4-T2, P4-T3, P4-T4, P4-T8, P4-T9, P4-T11, P4-T12 (merged and deployed, so the

Parallel-safe: no (one session, after the code tasks)

## Goal

An independent review of NetNet's security as it will launch, with every finding rated, reproduced
and routed, so the Founder decides each before go-live. The review changes no code; its fixes
become P4 tasks.

## Context

- Run in a **fresh session** that built none of P4 (like WORKFLOW Stage 6), as a security engineer.
  Inputs: architecture §6.1, §7 (contracts), §8 (auth and security), §10; CONVENTIONS §3, §6, §7;
  PRD N4, N5, N8, N9; the code and workflows as they are on `main`; production through its public
  surface only. No real person's data is read, ever; test accounts hold fictional data.
- Settled before the review (`decisions.md`, Architecture): **sign-up keeps saying that an email
  already has an account** (`422`). J1 lets a new person carry on unverified at once, so an
  existing address is revealed by the flow itself whatever the message says; sign-up is limited
  to 5 a minute per IP and the reset flow reveals nothing. The review confirms those two limits
  hold rather than reopening the choice.
- Already fixed: push endpoints only at the known push services, with no redirects (P4-T11).
- Scope, at least:
  - **Isolation (N4):** the isolation and RLS suites cover every route, tool and `ledger` table,
    including P4's new routes (`/api/cron/health`, `landing_view`) and scripts (`demo:load`); the
    registry tests would fail on a new one without a case.
  - **Auth and sessions:** cookie flags, the Origin check on every state-changing route, session
    lifetime, sign-out, password reset and verification tokens (single use, expiry), the
    re-authentication before deletion, rate limits as §8 states them, and whether any response
    differs by account existence beyond the settled sign-up case.
  - **Agent OAuth:** CIMD fetching (public HTTPS only, size and time limits, no private or
    link-local addresses after DNS resolution, redirects), DCR limits, redirect URI matching,
    PKCE S256 only, `resource` and `iss`, token audience and expiry, refresh rotation, revocation
    reaching the next call, the approval page's framing and its signed query, scopes dropped for
    OpenID requests.
  - **MCP:** limits per connection, input bounds (`record_values` 200, amounts, dates), errors that
    leak nothing, user text returned only as JSON string values (prompt injection, §8).
  - **Outbound requests:** every place the function or a workflow fetches a URL (FX sources,
    CIMD, push, Resend, Neon, Vercel), and whether any URL can be steered by a caller.
  - **Secrets (N5):** nothing in the repo or its history (run the secret scan), workflow logs mask
    every secret (the probe's token, the database URLs, the API keys), workflows' `permissions`
    are least-privilege, no `pull_request_target` or untrusted input reaches a shell, third-party
    actions are pinned.
  - **Headers and the browser:** CSP, HSTS, framing, the service worker's scope and that it caches
    nothing, the landing page's script and its event (abuse of the sessionless `landing_view` to
    inflate M10).
  - **Privacy in pipelines (N9):** `track()`, `log()`, Sentry scrubbing, `notify()` templates and
    the new `ops.health_alert`, the metrics output and the M12 reports.
  - **Data lifecycle:** deletion completeness (every user-keyed column, the re-keyed events, the
    30-day backup window), export contents, and P3-T13's open note that `ledger.ledger_state` has
    no key to `core.user` (a narrow race could leave a ledger for an erased id): recommend whether
    to close it before launch.
  - **Dependencies:** `pnpm audit --prod`, Renovate's open pull requests (PR #88), anything
    unmaintained.
  - **Operations:** backups encrypted to a key only the Founder holds; the restore path works
    (P4-T14 runs the drill); the production deploy can only be started by the Founder.
- Severity: Critical, High, Medium, Low, Info, each with steps to reproduce, expected vs actual,
  and a proposed fix with its size.
