# P4-T4: The daily health check, and the Founder's alert

Status: todo
Depends on: P4-T3 (the `netnet_metrics` login and `ops/metrics/n1-slo.sql`)
Parallel-safe: yes

## Goal

Once a day, every limit that can stop or slow the service is read and compared with its upgrade
trigger, and the Founder gets one email when any trigger fires, or when a figure cannot be read.
Silence then means the free tiers, the N1 SLO, the email allowance and the exchange rates are all
fine.

## Context

- Architecture §9.4 lists the triggers and their actions; §9.3 schedules the check daily at 01:00
  UTC, sharing the reminder run's database wake; §10 adds the N1 SLO breach, a security email
  unsent after 24 hours, and a failed FX fetch (§6.6: the previous rate stays in use and "an alert
  fires").
- No single process can read everything, and that is deliberate (`decisions.md`, Architecture):
  - Neon's consumption is read with the Neon API key, which is a GitHub secret (`NEON_API_KEY`,
    `vars.NEON_PROD_PROJECT_ID`, F7). It stays out of the function, where it would be able to
    delete the database.
  - The N1 SLO comes from `analytics.event`, which `netnet_app` cannot read (§6.1); `netnet_metrics`
    can (P4-T3's `DATABASE_METRICS_URL`).
  - Unsent security emails, exchange-rate dates and email counts are in `core`, which only the
    function reads.
  So the workflow gathers the first two and posts them to `/api/cron/health`; the function adds
  the rest, evaluates every trigger, and emails the Founder through the notification module, the
  only code that sends email (CONVENTIONS §6). §9.3 and §10 are rewritten to say so.
- `notify(userId, msg)` addresses an account; the Founder's alert goes to an operator address,
  `OPS_EMAIL` (F25), through a sibling `notifyOperator(msg)` in `apps/api/src/notify/` that uses the
  same email channel, a typed message and a template, so the no-amount template test covers it.
  It is a message kind §9.3 implies, added to §7.10's `Message` union (plan §1 rule 4).
- The day's email count must cover every kind (verification, reset, security, reminder), and
  Resend's free plan allows 100 a day and 3,000 a month. Count each email Resend accepts, in
  `core`, per UTC day, kept for at least 35 days (the existing `core.rate_limit` fixed windows, or a
  small table if those rows do not last).
- Vercel Hobby's usage: check whether Vercel's REST API reports it for a Hobby project with the
  existing `VERCEL_TOKEN`. If it does, the workflow reads it like Neon's; if not, the report says
  "Vercel: check the dashboard" and `ops/health.md` says how often. Record which in the report.
- The reminder's 60-a-day email cap (`REMINDER_EMAILS_PER_DAY`, `notify.ts`) being reached is a
  trigger of its own (§9.4).

## Interface contract

- `scripts/health.ts`, `pnpm health --env production`: reads Neon (`GET /projects/{id}`: the
  billing period's compute time and synthetic storage size; check the field names against Neon's
  docs source), runs `ops/metrics/n1-slo.sql` as `netnet_metrics`, posts
  `{neon: {computeCuHours, storageGb} | {unavailable: true}, slo: {calls, successRate, p95Ms} |
  {unavailable: true}, vercel?: {…}, testAlert: boolean}` to `POST /api/cron/health` with
  `CRON_SECRET`, prints the response, and exits 1 when any trigger fired.
- `POST /api/cron/health` (cron auth): adds `{securityEmailsUnsent24h, fxLatest: {ecb, fallback},
  emails: {yesterday, today, month}, reminderCapReachedYesterday}`, evaluates the triggers with a
  pure `evaluateHealth(figures, today)`, sends one `ops.health_alert` when any fired (or when
  `testAlert`), and answers `200 {triggers: [id…], figures}`. Counts, sizes and percentages only.
- Triggers (ids, thresholds from §9.4 and §10): `neon_compute` (≥ 60 of the month's 100 CU-hours),
  `neon_storage` (≥ 0.35 GB), `slo_latency` (7-day p95 > 1,500 ms), `slo_success` (7-day success
  < 99.5% over at least 50 calls), `emails_day` (≥ 70 yesterday), `emails_month` (≥ 2,100 this
  month), `reminder_cap` (60 reminder emails on a day), `security_email_unsent` (any older than
  24 h and younger than 7 days, unsent), `fx_stale` (ECB's latest more than 4 days old, or the
  fallback's more than 2), `vercel_limit` (any ≥ 70%, when readable), and `unreadable_<source>`
  for any figure that could not be read.
- `ops.health_alert`: `{triggers: TriggerId[], figures, test: boolean}`; subject "NetNet health:
  N to act on" (or "test"), one line per trigger with its figure and the §9.4 action. No user id,
  email, name or amount.
- `.github/workflows/cron-health.yml`: daily at `0 1 * * *` and `workflow_dispatch` with a
  `test_alert` boolean; secrets `CRON_SECRET`, `NEON_API_KEY`, `DATABASE_METRICS_URL`, variables
  `PUBLIC_ORIGIN`, `NEON_PROD_PROJECT_ID`; no `environment:` key; fails when a trigger fired.
- `ops/health.md` (new): what each trigger means and what to do; how to send a test alert.

      unreadable source fires its own trigger
- [ ] One email per run at most, to `OPS_EMAIL` only, with nothing personal in it; no email when
      nothing fired (unless a test)
- [ ] Every email kind increments the day's count when Resend accepts it, and only then
- [ ] After deploy with F24 and F25 set, a dispatched test run delivers the test alert to the

Deviations:
- **Neon storage.** `GET /projects/{id}`'s `synthetic_storage_size` is deprecated and always 0
  (Neon's API docs, checked 26 Oct 2026), so when it is 0 the script uses the default branch's
  `logical_size`: a lower bound on synthetic storage, which fires no later than the real limit. The
  0.35 GB trigger is unchanged. `compute_time_seconds` is current; /3600 is CU-hours.
- **Vercel.** No documented Hobby usage endpoint exists (`openapi.vercel.sh` has none; `/v1/usage`
  is undocumented and needs a token the workflow does not hold), so the script sends no `vercel`.
  `vercel_limit` exists in `evaluateHealth`, is tested, and is otherwise the dashboard check that
  `ops/health.md` sets weekly.
- The workflow passes `METRICS_EXCLUDE_USERS` in addition to the brief's listed secrets, so the N1
  SLO omits the probe account as `pnpm metrics` does.
- The day's counter is `core.rate_limit`'s `email:sent:YYYY-MM-DD` window, kept indefinitely (no
  migration); the brief allowed the existing windows.
- The returned `figures` carries `opsEmailConfigured: boolean`, so `evaluateHealth` stays pure and
  a missing F25 is itself a trigger; it is not personal data.
- `slo_latency` has no 50-call gate (the brief attaches that gate to `slo_success`), so it can fire
  on one slow call in a quiet week; `slo_success` requires 50 calls.
- `reminder_cap` uses the existing `countReminderEmailsToday` (the cap's own count) for yesterday,
  per the brief's `reminderCapReachedYesterday`.

Open issues:
- **F25 is unverified.** Until `OPS_EMAIL` is set in Vercel Production, every run reports
  `unreadable_ops_email` and the workflow fails without sending anything. Set it, then dispatch the
  workflow with `test_alert`.
- A failed alert send is logged (`ops_alert_failed`) but not reflected in the route's 200 response,
  so a dispatched test can be green with no email; confirm the inbox on that run.
- Vercel usage remains a manual, weekly check until its API reports Hobby usage.
- The Neon storage reading is a lower bound (logical, not synthetic), so it fires early rather than
  late; revisit when Neon exposes synthetic storage on the Free plan.
- `slo_latency` may be noisy at low call volume, as above.
