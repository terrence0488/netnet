# P4-T11: Push endpoints only at the browsers' own push services

Status: done
Depends on: none
Parallel-safe: yes

## Goal

The server sends web push only to the push services browsers actually use, and never follows a
redirect from one, so a crafted subscription cannot make NetNet's function call an address of the
caller's choosing.

## Context

- Today any `https:` URL is accepted as a push endpoint (`pushEndpointUrlSchema`,
  `packages/contracts/src/notifications.ts`), stored, and later POSTed to by the reminder run
  (`fetchPost`, `apps/api/src/notify/webpush.ts`), whose `fetch` follows redirects by default. The
  plan's P4 outline named this for the pre-launch security review; it is fixed first because the
  fix is clear.
- Architecture §7.10 names the services: Google's (Chrome, Android, and the Chromium browsers
  built on it), Mozilla's, Microsoft's, Apple's (Safari, and NetNet on an iPhone's Home Screen).
  Confirm each one's current endpoint hosts from its own documentation and from real
  subscriptions, and record the sources in the PR. Expected: `fcm.googleapis.com`,
  `updates.push.services.mozilla.com`, `*.notify.windows.com`, `web.push.apple.com`.
- Hosts match exactly or as a suffix at a dot boundary (`wns2-par02p.notify.windows.com` matches
  `*.notify.windows.com`; `evilnotify.windows.com.example` does not). No port other than 443, no
  userinfo, no IP literal.
- E2E and integration tests use a fake HTTPS push service (`e2e/server.ts`, P3's push tests). The
  allowlist is a dependency of the route and the channel, so tests pass their own; nothing in the
  environment can widen it in production.
- Existing rows: an endpoint stored before this change whose host is not on the list is revoked
  the next time a run would send to it, firing `push_disabled {by: browser}` as for a `410`, so the
  person falls back to email.
- The rejection is plain language with a next step (CONVENTIONS §11): this browser's push service
  is not one NetNet sends to; reminders will come by email.

## Interface contract

- `packages/contracts/src/notifications.ts`: `PUSH_SERVICE_HOSTS` (the list, one place) and
  `pushEndpointUrlSchema` checks it; `POST` and `PUT /api/notifications/endpoints` answer
  `400 VALIDATION_FAILED` with `fields.endpoint` for any other host.
- `fetchPost`: `redirect: 'error'`; a redirect counts as a failure of that send.
- The channel skips and revokes a stored endpoint whose host is not on the list.
- Architecture §7.10 ("How web push works", step 1) gains the rule in one line.

## Files in scope

## Done criteria

- [ ] A subscription at each listed service is accepted; any other host, an IP literal, a port, or
      userinfo is refused with a plain message, and nothing is stored
- [ ] A redirect from a push service is not followed and counts as a failed send
- [ ] A stored endpoint off the list is revoked at the next send, with `push_disabled {by:
      browser}`, and the reminder goes by email
- [ ] E2E push still passes against the fake service, and production cannot widen the list
- [ ] Tests written and passing: the schema (hosts, suffix boundaries, IPs, ports); the routes;
      the channel's skip-and-revoke; no redirect
- [ ] Follows CONVENTIONS.md

## Report (filled by engineer)
Files changed:
- `packages/contracts/src/notifications.ts`, `packages/contracts/src/notifications.test.ts`:
  `PUSH_SERVICE_HOSTS` (frozen: `fcm.googleapis.com`, `updates.push.services.mozilla.com`,
  `*.notify.windows.com`, `*.push.apple.com`), `isPushServiceUrl` (https, default port, no
  userinfo, no IP literal, exact host or `*.` suffix at a dot boundary) and
  `pushEndpointUrlSchemaFor`, which builds the create and update schemas over a given list. The
  production schemas stay exported over `PUSH_SERVICE_HOSTS`.
- `apps/api/src/http/notifications.ts`, `apps/api/src/http/notifications.test.ts`: the routes
  take `pushHosts` as a dependency (production's default is the frozen list) and parse POST/PUT
  with it; an endpoint off the list answers `400 VALIDATION_FAILED` with `fields.endpoint` in
  plain words before anything is written.
- `apps/api/src/notify/webpush.ts`, `apps/api/src/notify/webpush.test.ts`: `fetchPost` sends
  `redirect: 'error'`, so a redirect rejects and counts as a failed send; the channel checks
  every endpoint with `isPushServiceUrl` before building a request, revokes an off-list row
  through `store.revoke` (firing `push_disabled {by: browser}` once) and fails the send, so the
  reminder falls through to the other devices or email. `pushHosts` is a required dependency.
- `apps/api/src/notify/notify.ts`: the live wiring passes `PUSH_SERVICE_HOSTS` and
  `revokeEndpoint`; nothing about the list is read from the environment.
- `apps/api/test/notifications/channel.test.ts`, `apps/api/test/notifications/endpoints.test.ts`,
  `apps/api/src/http/notifications.test.ts`: an endpoint stored off the list is revoked at the
  next run and the reminder goes by email, the other devices still carry it, and the routes
  accept each listed service and refuse every other host, IP, port and userinfo.
- `apps/api/test/support/accounts-app.ts`: the test app passes its fake push service's host.
- `docs/03-architecture.md §7.10`: step 1 now states the rule in one sentence.

Sources for the list (read 2026-10-25):
- Google/FCM: the Firebase Admin SDK's `FCM_SEND_HOST = 'fcm.googleapis.com'`
  (`github.com/firebase/firebase-admin-node/blob/master/src/messaging/messaging.ts`) and
  Firebase's FCM HTTP v1 send documentation.
- Mozilla: autopush-rs's own docs name the endpoint host
  `https://updates.push.services.mozilla.com/`
  (`github.com/mozilla-services/autopush-rs/blob/main/docs/src/index.md`).
- Microsoft: the WNS overview says a channel URI uses the domain `notify.windows.com` and that
  the subdomain is subject to change, so the list matches the domain and any subdomain
  (`learn.microsoft.com/windows/apps/design/shell/tiles-and-notifications/`
  `windows-push-notification-services--wns--overview`).
- Apple: the Web Push documentation tells servers with egress limits to allow
  `https://*.push.apple.com`
  (`developer.apple.com/documentation/usernotifications/`
  `sending-web-push-notifications-in-web-apps-and-browsers`).

Tests run / results:

- The new and extended suites: `packages/contracts/src/notifications.test.ts` 13 cases,

Deviations:
- The Apple entry is `*.push.apple.com`, not only the brief's expected `web.push.apple.com`.
  Apple's own documentation tells servers to allow `https://*.push.apple.com`, and every host
  under it is Apple's; the brief's "expected" list is a starting point.
- The schemas are built by a new `notificationEndpointSchemasFor(hosts)`; the old exported
  schemas remain as production's, so nothing at the call sites changes.
- E2E push needed no change: `e2e/push.spec.ts` mocks the notification routes, so no fake
  endpoint ever reaches the allowlist there. The integration suites exercise the fake host.

Open issues:
- A stored row off the list is revoked only when a run next tries to send to it; there is no
  migration to sweep existing rows. Production is expected to have none, and the behaviour is
  tested.
- The list is frozen in code; changing a push service's host needs a release, by design.
