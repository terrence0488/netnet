# P4-T1: The demo household — a fictional balance sheet any account can load

Status: done
Depends on: none
Parallel-safe: yes

## Goal

One fixed, fictional, established-family balance sheet that can be loaded into a fresh account on
any environment with one command. The landing page's screen recording (F21), the directory
reviewers' test account (P4-T7) and the M12 harness (P4-T9) all use it, so the demo, the reviewers
and the benchmark see the same picture.

## Context

- PRD §2 P-C is the persona the benchmark is built on (§2.4: "the one P-C already runs every
  month"), and the recording shows "an agent answering a real question from a real balance sheet"
  (G-D1). The household is that balance sheet, entirely made up (CONVENTIONS §6).
- `apps/api/src/ledger/seed.ts` (`seedLedger`) is the pattern: written through `withUser` as a
  `system` write, audited, idempotent. That seed is a small isolation fixture; this one is a
  realistic picture and goes into a real, signed-up account.
- The household names local schemes ("CPF Ordinary Account"), which the N10 scan forbids outside
  `content/` and `docs/` (`test/n10/scan.ts`). It is data, not a flow, so it lives in `content/`
  with its own schema, validated by `content:check` and never published by `content:publish`.
- Values carry their own rates as given (`fxRate`, stored as `given_rate`, architecture §6.6), so
  every conversion, total and period is the same on local, preview and production, whatever the
  stored published rates. M12's ground truth depends on that.
- `DATABASE_URL` (the app's connection, as `netnet_app`) is a GitHub secret already
  (`deploy.yml`), so a manual workflow can load production without a secret reaching a chat.

## Interface contract

- `content/demo/household.json`, validated by a new `demoHouseholdSchema` in
  `packages/contracts` (accepted by `content:check`, skipped by `content:publish`):
  - country `SG`, base currency `SGD`, segment `established`;
  - 18–24 holdings covering every accessibility state and the §2.4 layers: SGD and USD bank cash,
    the three CPF accounts (retirement, locked), a primary home and its mortgage, a car and its car
    loan, a USD brokerage, unvested shares (equity, locked until they vest), crypto, a tax-advantaged
    wrapper, a credit card, a GBP account and a MYR account (instruments from several countries,
    J2), one holding answered "Not sure" (undecided), one archived holding;
  - monthly values over three years ending on a stated date, with deliberate gaps (carried
    months, J11), one value over 400 days old (stale, J9) and one holding with no value;
  - a few tags; every name and figure fictional and plausible for P-C (PRD §2: ~S$1M+ net worth,
    ~S$500K invested). No real institution names where a generic name serves.
- `pnpm demo:load --env <local|preview|production> --email <address>` (`scripts/demo-load.ts`):
  finds the verified account with that email, refuses unless it has no holdings, sets its country
  to `SG` as onboarding or Settings would (`init` for a ledger not yet made, else `changeCountry`,
  which with no holding starts over in SGD with SG's types), and writes the household through the
  Ledger as one `system` write per holding, values dated as in the file, each with its given rate.
  Prints counts only, never the email or a figure. Exit code 1 with a plain message otherwise.
- `.github/workflows/demo-load.yml`: `workflow_dispatch` with inputs `environment`
  (`production` only for now; previews use their own seed) and `email`; uses the `DATABASE_URL`
  secret; masks the email in the log; no `environment:` key (as `cron-*.yml`).
- `docs/03-architecture.md` §6.5 gains one line: `content/demo/` holds the fictional demo household,
  validated, never published.

## Done criteria

- [ ] `content:check` validates the household and rejects each invalid case the schema names
      (unknown universal type, a value in a currency with no given rate, a date after the end)
- [ ] Loading it into a fresh local account gives a Home, holding pages, Insights and a
      `get_financial_context` that show every feature named above (could use, locked with until,
      undecided, stale, carried months, several currencies); a golden test pins the loaded
      account's `compileContext` output for the file's end date
- [ ] A second load into the same account refuses and writes nothing; a load into a missing or
      unverified account refuses
- [ ] Nothing in the script's or the workflow's output carries an email, a name or an amount
- [ ] Tests written and passing: schema cases; the loader against Postgres (counts, idempotence,
      refusal, audit rows as `system`, isolation: another account is untouched); the workflow's
      shape (`test/workflows/`)
- [ ] Follows CONVENTIONS.md

## Report (filled by engineer)
Files changed:
- `content/demo/household.json` (new): the fictional P-C household. SG / SGD, segment
  `established`, 21 holdings and 686 values from 2023-10-31 to 2026-09-30; SGD, USD, GBP and
  MYR; four tags; one archived holding; one with no value; one undecided; one stale over 400
  days; deliberate carried months. Every foreign value gives its own `fxRate`, so the picture is
  the same on every environment without a published-rate lookup.
- `content/demo/household.context.json` (new): the golden `compileContext` output at the
  household's end date, byte for byte.
- `packages/contracts/src/content.ts`, `packages/contracts/src/content-demo.test.ts`: the
  `demoHouseholdSchema` and `validateDemoHousehold`, which check the shape against the country,
  its currency and the live pack types: unknown universal type, missing given rate, a date after
  the end, a base-currency rate, out-of-order or duplicate dates, too many decimals, unknown or
  repeated tags, an accessibility answer on a liability, unknown fields and a pack type of
  another universal type.
- `scripts/content-check.ts`, `test/content/demo.test.ts`: `content:check` validates the
  household and never reads it for publishing; the tests also cover a broken file, invalid JSON
  and a content directory without a household.
- `apps/api/src/ledger/demo.ts` (new), `apps/api/src/db/demo.ts` (new): the loader.
  `loadHousehold` writes the country, tags and every holding through `addHolding`/`insertValues`
  in one `withUser` transaction as `system`; `loadDemoHousehold` finds the verified account with
  the email, refuses one with any holding (archived included), sets the profile as onboarding
  would, and returns counts only. `DemoRefused` messages carry no name, email or amount.
- `apps/api/src/ledger/holdings.ts`, `apps/api/src/ledger/values.ts`: `addHolding` and
  `insertValues` extracted from `createHolding` and `insertValue`, so the loader runs the same
  code as the API and MCP; behaviour is unchanged.
- `apps/api/test/ledger/demo.test.ts` (new): 17 cases over Postgres: counts, country/currency/
  types, audit rows as `system`, given rates, accessibility, context features, carried months,
  the golden, a second load, missing/unverified/an archived-only account, a ledger with no
  holding, isolation, and the script's output and exit codes.
- `scripts/demo-load.ts` (new), `package.json`, `.github/workflows/demo-load.yml` (new),
  `test/workflows/demo-load.test.ts`: `pnpm demo:load --env <local|preview|production> --email
  <address>` and the manual production workflow. The workflow refuses anything but one address
  before echoing, masks it, and passes it through `GITHUB_ENV`; the script prints counts only.
- `docs/03-architecture.md` §6.5 and `CLAUDE.md` → Commands: `content/demo/` and the command.
- `.prettierignore`: the golden is left alone, as core's golden files are.
