## Goal

Everything the launch needs, except going live itself (Stage 8), is on production and checked: the
landing page, the metrics per segment, the free tiers watched, ten packs reviewed, the guides
current, the listings and the launch note ready, the M12 result in hand, backups proven to
restore. Then `stage: test P4` runs.

## Context

- Plan §P4's checkpoint and criteria. P3-T10 is the pattern: a responsive sweep, then the
  checkpoint verified on production, with the boxes that need the Founder stated as steps.
- Production stays unannounced (`noindex`, P4-T2) until Stage 8, which removes it.
- `decisions.md` (Delivery): production deploys trust the merged pull request's green Checks while
  one pull request lands at a time; "when all phases are delivered, revisit: re-enable the
  main-green gate or take GitHub's merge queue". The merge queue needs an organisation on GitHub
  Enterprise Cloud for a private repository, which this personal repository is not, so the deploy
  waits for `main`'s own CI to be green on the commit it deploys. The decision is rewritten to say
  so.
- Architecture §9.3: a spent Actions budget stops every job at once, reminders and backups
  included. The schedules use about 400 minutes a month, before CI.
- `ops/backup.md` describes the daily encrypted backup. Only the Founder holds the key (F14), so
  only the Founder can run a restore.

## Interface contract

- `deploy.yml`: before deploying, it requires the `Checks` result of `main`'s CI on the commit
  being deployed to be green, and stops with a plain message otherwise.
- `ops/launch-readiness.md` (new): the checklist below with its results and dates, the evidence
  for each, and anything left for Stage 8.
