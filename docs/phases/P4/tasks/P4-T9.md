# P4-T9: The M12 harness — NetNet against a spreadsheet, on a weak model, scored blind

Status: todo
Depends on: P4-T1 (the household); F22 (the API key, and the Founder's approval of each run's spend)
Parallel-safe: yes

## Goal

A repeatable benchmark that answers A13: with identical data, does a weak model answer better
connected to NetNet than handed the data as a spreadsheet? It runs a fixed question set in both
arms, scores the answers blind, and reports whether NetNet wins at least 80% of pairs and never
scores worse on fabrication (PRD M12).

## Context

- PRD §2.4 (the benchmark P-C already runs; the four layers a spreadsheet cannot carry), M12
  (blind A/B, fixed dataset and question set, numeric correctness, appropriate qualification,
  absence of fabrication, a deliberately weak model), J8 (the blind comparison). Architecture §12
  risk 9: the harness and paid calls; the Founder approves each run's spend.
- **N2 holds:** the harness is a tool the Founder runs, never part of the product. It lives in its
  own workspace package, `ops/m12/`, so the Anthropic SDK is never a dependency of `apps/*` or
  `packages/*`, and a lint rule refuses `@anthropic-ai/sdk` there.
- **The models.** The answering model is the weakest current Claude, `claude-haiku-5-5`, at effort
  `low` (`output_config.effort`), so a lift cannot be the model's. `--model` also accepts
  `claude-haiku-4-5` for a second weak run. The judge is `claude-opus-5-5` at effort `high`. Use
  these exact ids; check them against the Models API at start and stop if one is missing.
- **The NetNet arm.** The harness starts the built app locally (as `e2e/server.ts` does) against a
  scratch Postgres, signs up an account, loads P4-T1's household into it (`demo:load` logic), and
  connects as an MCP client the way a real agent does (discovery, DCR, PKCE, the approval API with
  the account's session, as `e2e/agent.ts`'s fake agent). The API's MCP connector needs a public
  URL, so tools are proxied client-side: the harness lists NetNet's tools, gives each to the model
  as a client tool (name, description, input schema as served), runs every `tool_use` through the
  MCP client, and returns the tool result's text, which is what Claude gives the model. The
  server's instructions go in the system prompt, as a client would put them. Its own loop, not the
  SDK's tool runner, so every call and its latency is logged. Ten rounds at most per question.
- **The spreadsheet arm.** The same household as a person keeps it: one CSV, a row per holding
  (name, kind, currency) and a column per month-end with the amount in the holding's currency,
  blank where nothing was recorded, and the rates the household used in their own block. None of
  NetNet's derived layers: no accessibility, reasons, totals, staleness or conversions. Uploaded in
  the user turn as a document, with the same system prompt minus the tool instructions. Built from
  `content/demo/household.json`, so both arms hold identical data.
- **Both arms** get the same system prompt (a capable assistant helping a person with their own
  finances; today's date, the household's end date), the same question, and no other help.
- **Questions** (`content/demo/m12-questions.json`, beside the household, because they name local
  schemes): about 30, across the four layers and the PRD's examples. Affordability ("can I afford a
  S$120K car?": could-use, not net worth), progress (change since last quarter, last year),
  exposure (USD share), debt burden, locked money and until when, concentration, a stale value's
  effect, the undecided holding, and questions the data cannot answer (salary, a bank not tracked),
  which test fabrication. Each has its ground truth computed from the household by `core`
  (`compileContext`, `periods`, `position`) and stored with a tolerance, plus the qualifications a
  good answer makes (stale, undecided, incomplete).
- **Scoring, blind.** Numeric correctness is checked against the ground truth: the judge extracts
  the answer's figures into a structured output, and the harness compares them. Qualification and
  fabrication are scored by the judge from a rubric, given the question, the ground truth and the
  two answers as "A" and "B" in a seeded random order, never told which arm is which or that NetNet
  exists. A pair goes to the higher total; a tie is no win. The harness also writes a blind sheet
  of 10 seeded pairs for the Founder to score by hand, and reports the agreement with the judge.
  The questions, ground truth and rubric are committed before the first paid run and carry a
  version; a change after a run is a new version, every report names its version, and nothing is
  tuned toward a result.
- **Spend.** Before any call that costs, the harness counts tokens (`messages.countTokens`) for a
  dry pass, prices it from the per-token rates in its config, prints the estimate, and runs only
  with `--approve-spend <usd>` at or above it; it stops if actual spend passes that figure.
  Expected: about US$2 a run on these models (well under US$10 for three runs), mostly the judge.
- **Where it runs.** On the Founder's computer with `ANTHROPIC_API_KEY`, or as a manual GitHub
  workflow with that secret (F22), so the key never reaches a chat or a file. Reports never contain
  the key, and contain only fictional data.

## Interface contract

- `ops/m12/` (workspace package `@netnet/m12`): `pnpm m12 --approve-spend <usd> [--model <id>]
  [--runs <n>] [--seed <n>] [--dry-run]`.
- `content/demo/m12-questions.json`, validated by `content:check` with a schema in
  `packages/contracts`.
- Output in `ops/m12/runs/<date>-<seed>/` (gitignored except `report.md`): `transcripts.jsonl`
  (both arms, every turn and tool call), `scores.json`, `blind-sheet.md`, `report.md` (pairs won,
  the 80% line, fabrication per arm, per-layer results, spend, model ids).
- `.github/workflows/m12.yml`: `workflow_dispatch` with `approve_spend`, `model`, `runs`; secret
  `ANTHROPIC_API_KEY`; uploads the run folder as an artifact. No `environment:` key.
- `docs/03-architecture.md` §12 risk 9 states where the harness lives and that it is outside the
  product (N2).
