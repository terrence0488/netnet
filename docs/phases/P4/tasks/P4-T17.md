## Goal

An unauthenticated caller can no longer make the function fetch unbounded distinct URLs or create
unbounded `core.oauth_client` rows. (The 30-day purge is P4-T20.)

## Context

- P4-T13's M-1 (`docs/phases/P4/security-review.md`): the authorize path resolves an unknown CIMD
  `client_id` before it looks for a session; DCR is limited to 10 an hour per IP, but authorize has
  no limit, so a script can make the function GET any public HTTPS URL and persist one
  `core.oauth_client` row per unique valid document. On Neon Free's 0.5 GB that is a
  storage-exhaustion path, alerted at 0.35 GB but not stopped.
- The transport itself is sound (public HTTPS only, 5 s timeout, 5 KB, no redirects, private and
  link-local addresses refused). This task bounds the volume and the persistence, not the
  transport.

## Interface contract

- `GET /api/auth/oauth2/authorize` is rate-limited per IP (for example 60/min, one
  `deps.rateLimit('oauth-authorize:ip:…', 60, 60)` line, like the other routes).
- New CIMD client rows are capped (for example 60 an hour globally) and refused with a plain
  `temporarily_unavailable` when the cap is reached; a known client still resolves.
- No new secret; no change to the transport or to PKCE/redirect matching.

Deviations:
- One limit beyond the brief's two: a *new* CIMD document also gets a per-IP limit (20/hour). The
  brief's 60/min authorize limit alone would let a single IP create 60 rows an hour; the tighter
  per-document-IP limit is what makes the 25-URL probe stop well before 25 rows. The transport,
  PKCE and redirect matching are untouched, and no secret was added.
Open issues:
- Residual race: two concurrent unknown documents at 59 rows can both pass the cap before either
  row exists, so overshoot is bounded by in-flight requests, never unbounded. Worth a follow-up if
  it matters after launch.
