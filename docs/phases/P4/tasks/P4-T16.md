# P4-T16: Sentry holds no SQL, parameters or free text

Status: done
Depends on: P4-T13 (the review's H-1)
Parallel-safe: yes

## Goal

Every event Sentry receives from the API and the web app carries no SQL, bound parameter values,
holding or type names, amounts or free text — only the error's class, stack and NetNet's own
fields.

## Context

- P4-T13's H-1 (`docs/phases/P4/security-review.md`): `scrubSentryEvent()` redacts email addresses
  but keeps each `exception.values[].value`. Drizzle's `DrizzleQueryError` carries the SQL and its
  bound parameters in that message (`… params: usr_…,1`; an insert would carry a name and an
  amount), and `reportError()` sends it to Sentry on every unexpected failure. That contradicts
  PRD N9, CONVENTIONS §6 and the published privacy page's "Amounts, names or text in analytics,
  logs or error reports" — never.
- Architecture §10: `sendDefaultPii: false`, `beforeSend` drops bodies, query strings and
  breadcrumb text; no session replay. The log line is already safe (`errorClass()` keeps the class
  name and SQLSTATE only); this task closes the Sentry path.
- The same scrub exists on the web side (`apps/web/src/sentry.ts`); fix both so one implementation
  cannot drift from the other's promise.

## Interface contract

- `scrubSentryEvent()` keeps `type`, the stack and NetNet's own whitelisted fields; it replaces
  every `exception.values[].value` with a fixed placeholder (for example
  `'[redacted by NetNet]'`), and drops `extra` and `contexts`.
- No SQL text, `params:` list, holding/type/tag name, amount, email or free text may remain in any
  field Sentry receives.

## Files in scope

- `apps/api/src/lib/sentry.ts`, `apps/api/src/lib/sentry.test.ts`
- `apps/web/src/sentry.ts`, `apps/web/src/sentry.test.ts`
