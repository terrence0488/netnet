# P4-T3: The metrics, per segment

Status: todo

Parallel-safe: yes

## Goal

The Founder can read every §3.2 metric that comes from live usage, per segment, with one command or
one click: M1–M11 and M13 (M13 per channel), with the §3.3 kill readings flagged on P-B and P-C,
and the M10 funnel from landing to verified sign-up (G-D4).

## Context

- PRD §3.2 defines each metric "as instrumented"; §3.3 reads the kill criteria on P-B and P-C only,
  never on the blend; §3.5 lists the events and says per-segment readings join `signup_started` and
  `account_created` (which carry `unknown`) to the account.
- Architecture §7.7 and §10: `ops/metrics/*.sql`, run as `netnet_metrics`, computes the metrics
  from `analytics.event` alone, so no metric can read a balance. `netnet_metrics` exists (migration
  `0001`, `apps/api/src/db/bootstrap.ts`) with `SELECT` on `analytics` only, but is created
  `nologin` and has no password.
- **"Signup" means a verified account** (§3.2), and no event says when an email address is
  verified: `account_created {method}` fires at creation, verified already for Google and Apple,
  not yet for email. So this task adds one event, `email_verified` (no props, server, fired once
  when an email sign-up's address is verified), and adds it to PRD §3.5 and architecture §7.7
  (`decisions.md`, Users and measurement). A signup is then an `account_created` with `method`
  `google` or `apple`, or an `email_verified`. Accounts created before the event shipped are not
  in the launch window.
- A person's segment is the one on their events after onboarding (set once, never changed by us,
  §3.5); before that, and when skipped, `unknown`.
- Checks the engineer must make against the code, and state in each SQL file's header with any
  approximation: `value_recorded` fires once per value, not per call (M5's denominator);
  `value_corrected.age_at_correction` is whole days, so "within 48 h" is `≤ 2`; whether
  `push_enabled` can fire twice for one device (M13's "push on for ≥ 1 device" nets `push_enabled`
  against `push_disabled` per person); `visitor` is unique per UTC day only, so M10's visitors are
  the sum of daily uniques, which overstates repeat visitors across days (say so in the output).
- The probe account (`ops/probe.md`) is a real account with fictional data: exclude it from every
  metric by its user id, given as a parameter, never committed.
- The deploy workflow runs `db:bootstrap` before every migration, so a metrics password can be set
  the same way as the app's.

## Interface contract

- `email_verified`: a server event in `packages/contracts/src/events.ts`, fired by the auth hook
  when Better Auth marks an email verified (once per account), through `track()` with the
  account's segment.
- `ops/metrics/m01-signups.sql` … `m13-comeback.sql`, plus `m10-funnel.sql` (daily: landing
  visitors → `signup_started` → `account_created` → verified) and `n1-slo.sql` (7-day success rate
  and p95 from `agent_tool_called`, used by P4-T4). Each takes `:from`, `:to` and
  `:exclude_users`, and returns rows of `(metric, segment, numerator, denominator, value)`, or
  `(metric, channel, …)` for M13. Every header states the PRD definition and how the SQL reads it.
- `pnpm metrics --env <local|preview|production> --from <date> [--to <date>]`
  (`scripts/metrics.ts`): connects with `DATABASE_METRICS_URL` (as `netnet_metrics`), runs every
  file, prints one table per metric with P-A, P-B, P-C, unknown and blended columns, its target,
  and, for M1, M3, M6 and M7, the kill threshold read on P-B and P-C. Exclusions from
  `METRICS_EXCLUDE_USERS` (comma-separated ids). Prints aggregates only.
- `db:bootstrap`: when `NETNET_METRICS_DB_PASSWORD` is set (same rule as the app's), `netnet_metrics`
  gets `login` and that password; unset, it stays `nologin`. `deploy.yml` passes the secret
  `NETNET_METRICS_DB_PASSWORD_PROD`.
- `.github/workflows/metrics.yml`: `workflow_dispatch` with `from` and `to`; runs `pnpm metrics
  --env production` with the `DATABASE_METRICS_URL` and `METRICS_EXCLUDE_USERS` secrets and writes
  the tables to the job summary. No `environment:` key.
- PRD §3.5 and architecture §7.7 (the event, and §7.7's note on M1), §10 (the workflow) rewritten
  in place.
