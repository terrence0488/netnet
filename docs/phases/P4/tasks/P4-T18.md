# P4-T18: Show who is asking — a CIMD client's host, and its name as unverified

Status: todo
Depends on: P4-T13 (the review's M-2)
Parallel-safe: yes

## Goal

The approval page and the security email show a CIMD client's host, and treat its self-chosen name
as unverified unless the host matches a named guide, so a person can tell who is asking before
granting `ledger.read` and `ledger.write`.

## Context

- P4-T13's M-2 (`docs/phases/P4/security-review.md`): `apps/api/src/auth/approval.ts:175` sets
  `nameVerified: p.registration === 'cimd'` — but a CIMD name is text in a document the client
  hosts at a URL it chose. An attacker can host a document at `https://attacker.example/client.json`
  named "Claude" and NetNet's own page says **"Claude wants to connect to your NetNet"** with no
  caveat and no host, above the Allow button. The API already returns `host` and `client`; the page
  discards them.
- Architecture §7.10: an agent's registered name is untrusted third-party text, escaped in email
  and shown on a lock screen only when short and plain. CONVENTIONS §6 has the same rule.
- The security email (`apps/api/src/notify/templates/security.ts`) appends its caveat only for DCR;
  use the same rule as the page.

## Interface contract

- `nameVerified` is true only when the client matches a named guide's host (the `claude`/`chatgpt`
  classification with that guide's `matchHosts`); every other CIMD and DCR client is unverified.
- The approval page shows the client's `host` under the title (plain text, escaped), and shows the
  existing "NetNet can't verify this name" caveat whenever `nameVerified` is false.
- The security email uses the same rule for its caveat and names the host when it has one.
- No schema or API-shape change unless a field is missing from the approval response; if it is,
  add it additively.

## Files in scope

- `apps/api/src/auth/approval.ts` and its tests
