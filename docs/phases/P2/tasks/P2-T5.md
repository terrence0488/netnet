# P2-T5: Holding page complete

Status: in-progress

## Goal

A holding page with its own trend, change over the baseline and paged history; values edit and
delete; holdings archive, unarchive and delete; tags assign; the connect flow starts here too.

## Context

P1-T16 built the first holding page; P1's Ledger, REST and MCP layers cover holding CRUD and
`record_values` (J6). This task adds the web surface for value edit/delete, archive and delete,
plus tag assignment, per PRD J2, J3, J4 and the J5 holding entry. Rule 2 of the plan holds: any
capability added here lands in the Ledger, REST and MCP together — verify each contract below
and implement what P1 did not, so the agent is never behind the UI.

Seam with P2-T6: T6 owns type/tag CRUD and `tagIds` on holding create; this task owns `tagIds`
on holding update and the holding page's tag UI.

## Interface contract

- `GET /api/holdings/:id/values?cursor&limit≤200`, newest first (architecture §7.2; verify
  paging, add if missing).
- `PATCH /api/values/:id` / `DELETE /api/values/:id` + `Ledger.updateValue` / `deleteValue` +
  MCP `update_value` / `delete_value` (architecture §7.2–§7.4). Editing onto an occupied date
  follows J3's same-date rule: last write wins, with the `SAME_DATE_REPLACED` warning. Edits
  fire `value_corrected {original_source, age_at_correction}` (architecture §7.7).
- `PATCH /api/holdings/:id {…, tagIds?, archived?}`: archived holdings leave all totals and
  charts but keep history and unarchive (PRD J2).
- `DELETE /api/holdings/:id` from the web with a confirm step: holding and history removed, the
  action audited in the rows (the log screen is P3).
- `POST /api/agent/attempts {…, entry: "holding"}` opens the same connect flow (PRD J5).
