# P2-T6: Types and tags

Status: todo
Depends on: none
Parallel-safe: yes

## Goal

Types and tags add, rename, merge and delete from the web, with holdings following every
change; the Add form takes tags.

## Context

P1 carries types and tags in the snapshot and exposes them to the agent (J6); pack default
types are added on country confirmation (architecture §6.7). What is missing is the person's
own taxonomy management (PRD J2). Labels follow the current pack until the user renames: no
name is stored until then (architecture §6.3). A tag delete removes it from the holdings that
carry it or merges it into another and is never refused; each holding's change is audited
(decision register). Rule 2 of the plan holds: verify each contract below and implement what
P1 did not, across the Ledger, REST and MCP together.

Seam with P2-T2: this task lands first (wave 1) and owns `tagIds` on `POST /api/holdings`; T2
adds `via` beside it in wave 2.

## Interface contract

- `POST /api/types` · `PATCH /api/types/:id` · `DELETE /api/types/:id?moveTo=` +
  `Ledger.upsertType` / `deleteType` + MCP `upsert_type` / `delete_type` (architecture
  §7.2–§7.4). Delete moves the type's holdings to `moveTo`; nothing is orphaned.
- `POST /api/tags` · `PATCH /api/tags/:id` · `DELETE /api/tags/:id?mergeInto=` +
  `Ledger.upsertTag` / `deleteTag` + MCP `upsert_tag` / `delete_tag`. Delete removes or merges,
  never refused.
- `POST /api/holdings` and `PATCH /api/holdings/:id` accept `tagIds`; the Add form offers the
  person's tags.

## Files in scope

- `apps/api/src/ledger/**`, `apps/api/src/http/**`, `apps/api/src/mcp/**` (taxonomy only, where
  P1 did not build it) plus `tagIds` on the holdings routes
- `packages/contracts/**` (taxonomy schemas, only where missing)
- `apps/web/src/routes/**` and components (taxonomy screens and the Add form's tags only)
- E2E and integration tests for this task
