# P1-T11: Accounts — sign-up, verification, sessions, profile and notify()
Status: todo
Depends on: P1-T2 (verdict), P1-T4, P1-T7, P1-T8
Parallel-safe: yes

## Goal
People create an account with an email and a password and are asked nothing else, carry on
unverified while a verification email goes out, sign in, reset a password and sign out. Each account
has a profile (country, time zone, segment, onboarding state). Every email goes through `notify()`.

## Context
- Read: PRD J1 (sign-up asks nothing else; verification never blocks except before connecting an
  agent; a returning user resumes onboarding; the sign-up events), §2.3 rule 2 (the IP lookup on our
  server). Architecture §4 (the Accounts and Email rows), §6.2 (`profile`, Better Auth's tables),
  §7.2 (`/api/auth/*`, `GET /api/geo`, `GET/PATCH /api/me`), §7.10 (`notify()`, channels, templates),
  §8 (web sessions, passwords, rate limits). CONVENTIONS §3, §6, §7, §11. The spike's verdict
  (`docs/phases/P1/spike.md`) for Better Auth.
- **Google and Apple are P2.** Configure Better Auth so adding them is configuration.
- **`notify()` and the email channel are built here.** Verification and reset emails also go through
  `notify()`, as two more kinds, `account.verify_email` and `account.reset_password`: email only,
  unaffected by the Reminders switches. That keeps CONVENTIONS §6 true (every message to a person
  goes through `notify()`) and the template privacy test universal. Add both kinds to architecture
  §7.10's `Message` type (an additive change, plan §1 rule 4). The security email is P1-T13's; the
  comeback reminder is P3's.
- **Email in previews and tests:** a fake channel captures messages. A preview sends real email only
  to the addresses in `EMAIL_PREVIEW_ALLOW` (F10); anything else is captured and logged without its
  content.
- **Country:** `GET /api/geo` reads `x-vercel-ip-country`, never a third-party service. `PATCH /api/me
  {country}` validates against `countries.json` from the content store and records the country
  (a country with no pack still gets recorded). Initialising the ledger on the first confirmation is
  P1-T12's.
- **Time zone:** the browser's at sign-up, `UTC` if none; updated whenever the browser reports another.
- **Segment:** `starting_out | accumulating | established | unknown`, set once in onboarding, never
  changed by us afterwards (PRD §3.5).
- **Onboarding state:** a string with P1's values `country`, `segment`, `done`; P2 adds its steps.
- **Rate limits:** a shared helper over `core.rate_limit` (sign-in 10/min per IP and email, sign-up
  5/min per IP). P1-T13 and P1-T15 reuse it.
- **Events:** `account_created {method: email}` from the auth hook (`signup_started` is the client's,
  P1-T14).

## Interface contract
- `/api/auth/*`: Better Auth's email and password endpoints (sign-up, sign-in, sign-out, verify,
  send verification, forgot and reset password), with the cookie of architecture §8.
- `GET /api/me` → `{email, emailVerified, country, baseCurrency, segment, timeZone,
  onboardingState}`; `PATCH /api/me` accepts `country`, `segment` (only while `unknown`), `timeZone`,
  `onboardingState`.
- `apps/api/src/auth/session.ts`: `requireSession(c) → {userId, emailVerified}`. The `userId` given to
  `withUser` comes only from here or from an agent's token (CONVENTIONS §3).
- `apps/api/src/lib/rate-limit.ts`: `rateLimit(key, limit, windowS)` → allowed, or `RATE_LIMITED
  {retry_after_s}`.
- `apps/api/src/notify/`: `notify(userId, msg: Message) → Delivery` (architecture §7.10), the
  `Channel` interface, `emailChannel` (Resend: `RESEND_API_KEY`, `EMAIL_FROM`), and templates
  rendering `{subject, html, text, headers}`.

## Files in scope

## Done criteria
- [ ] Sign-up with an email and a password only (at least 8 characters, no composition rules):
      account, profile (with time zone) and the session exist; the verification email is sent through
      `notify()`; the user is signed in at once.
- [ ] Unverified users can use everything but the start of an agent connection; `emailVerified` is
      exposed for P1-T13's `EMAIL_NOT_VERIFIED`.
- [ ] Reset never reveals whether an account exists. Rate limits enforced (fake clock).
- [ ] `GET /api/geo` from the header; `PATCH /api/me` validation, including an unpacked country.
- [ ] Every template passes the privacy test: no digits with a currency, no user-supplied names.
- [ ] Cookie `HttpOnly`, `Secure`, `SameSite=Lax`; an Origin check on state-changing requests;
      isolation cases for `/api/me`.
- [ ] `account_created` fires with `method` and `segment: unknown`.
- [ ] Follows CONVENTIONS.md

Deviations:
- Outside the listed files: `db/schema.ts`, `db/auth-adapter.ts`, `db/profiles.ts` (only
  `apps/api/src/db/**` touches `core`); `ledger/base-currency.ts` (`/api/me`'s `baseCurrency` is a
  ledger read); `http/geo.ts`; `lib/env.ts`, `lib/after-response.ts` (`inBackground`, for Better
  Auth's hooks, which have no Hono context), `lib/context.ts`; the contracts (REST schemas live
  there, CONVENTIONS §11); `app.ts`.
- No `profile` change in the migration: it already had P1's columns. No foreign key to `core.user`,
  because the seed and the migrations test write a profile for a user who has no account.
- A message carries Better Auth's `token`, not a URL. The template builds the link on
  `publicOrigin()`, so a `callbackURL` a client sends never reaches an email. Verifying lands on
  `/app/` (`?error=…` if the link failed); the reset link goes through Better Auth's GET, which
  checks the token, to `/app/reset-password?token=…` (or `?error=INVALID_TOKEN`).
- The sign-up's verification email is sent from Better Auth's user `create.after` hook, once
  sign-up's transaction has committed, not by `sendOnSignUp`: `notify()` reads the address from
  `core.user`, which is not committed while the built-in send runs. Resends use
  `sendVerificationEmail`. Both, and the reset email, run after the response.
- A refused Origin answers `401 UNAUTHENTICATED`: §7.5 has no code for it. Without `Origin`,
  `Sec-Fetch-Site` other than `same-origin`/`none` is refused; a request with neither passes (no
  browser sent it). `/mcp` and `/.well-known` are not checked.
- Limits §8 does not number: reset and verification emails, 5 a minute per IP each. Sign-in is one
  key per IP and email together (§8's "per IP+email"). Request bodies to `/api/auth` are capped at
  4 KB, `PATCH /api/me` at 1 KB.
- `/api/auth` serves only POST `sign-up/email`, `sign-in/email`, `sign-out`,
  `send-verification-email`, `request-password-reset`, `reset-password`, and GET `verify-email`,
  `reset-password/:token`, `get-session`; Better Auth's others answer `NOT_FOUND` (`update-user`
  would store a name). Their responses keep Better Auth's error body `{code, message}` (such as
  `PASSWORD_TOO_SHORT` 400, `INVALID_EMAIL_OR_PASSWORD` 401, an existing email 422); our limits
  and the Origin check answer in §7.2's shape.
- Sign-up says when an email already has an account (422), as Better Auth does with auto sign-in.
  Only reset must not reveal it, and does not (same status and body, the email only to a real one).
- Sign-up's body is `{email, password, timeZone?}`: the route fills Better Auth's required `name`
  with `""`, and the user hook keeps `name` empty and `image` null whatever is sent. A missing or
  invalid time zone records `UTC` instead of refusing the sign-up.
- `PATCH /api/me` answers with the profile, as `GET` does, not `{result, dataVersion, warnings}`:
  the profile is not in the ledger. Sending the segment already set is accepted; another one is
  `400 fields.segment`, and nothing in that request is applied.
- No session keeps an IP address or a user agent. Better Auth's own rate limiter is off
  (`core.rate_limit` instead), and its logger is replaced by `auth_error` lines without the
  message, which can carry an address. The verification link lasts a day, the reset link an hour.
- `BETTER_AUTH_SECRET` is required on Vercel; a local run without it makes one per process.
- New dependency: `better-auth` 1.7.7, the spike's verdict (architecture §4). It replaces writing
  sign-up, password hashing, sessions, verification and reset ourselves; 2.1 MB unpacked, plus
  `kysely`, `jose`, `@noble/*` and `better-call`; MIT, released weekly by an active team. Resend is
  called with `fetch`, so no SDK.
