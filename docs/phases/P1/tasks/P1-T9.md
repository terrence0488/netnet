# P1-T9: Core — compileContext, the agent's context
Status: done
Depends on: P1-T6
Parallel-safe: yes

## Goal
`core.compileContext()` turns a user's ledger data into architecture §7.5's document: the four
context layers, ordered by importance, at most 8 KB, byte-identical for identical input. This is the
differentiator (PRD §2.4), and its golden files are its contract.

## Context
- Read: PRD §2.4 (the four layers; dense, not comprehensive; facts and structure, never judgement),
  J8 (every criterion), N11. Architecture §7.5 (shape, 8 KB, order, holdings largest first capped at
  25, the rest summarised by type with a pointer to `list_holdings`), §6.7 (labels follow the current
  pack; outcomes and reasons stay as applied), §8 (the Prompt injection and Untrusted agent names
  rows). CONVENTIONS §9 (golden files).
- `meaning` is the chain's `meaning[universal]`, pack text, never hard-coded, given once per type in
  `types` rather than on every holding (the Founder's decision). `answer_guide` is fixed
  text in core: it is an opinion about the interaction, universal, not local knowledge.
- `written_by` is `web`, `system`, or `agent:<name>`, where `<name>` is the guide name for a
  connection classified `claude` or `chatgpt`, and `other` for anything else. An agent's registered
  name is untrusted text (§8) and never reaches another agent's context.
- `picture.freshness` is one of `empty`, `fresh`, `some_stale`, `mostly_stale` (more than half
  stale). `picture.notes` are at most five fixed English templates, filled with numbers and holding
  names only, most important first. Undecided holdings always produce a note: an affordability
  answer must be qualified (J2).
- **Size budget.** Past 8 KB, drop in this order until it fits: holdings beyond the cap, concentration
  entries beyond five, notes beyond three. Test with a 200-holding account.
- Amounts are JSON numbers in major units, rendered from minor units by `fromMinor`. Keys appear in
  §7.5's order. Nothing depends on object insertion accidents: sorting is explicit, with ties broken
  by id.

## Interface contract
```ts
compileContext(data: ContextInput, chain: Pack[], today: string,
               opts: { baseline?: Baseline }): FinancialContext
```
- `ContextInput` = `{baseCurrency, holdings, values, types, tags, connections: {id, client,
  guideName?}[]}`, which `Ledger.context()` returns (P1-T10).
- `FinancialContext` is §7.5's shape as a zod schema in `packages/contracts/src/context.ts`; it is
  `get_financial_context`'s `outputSchema` (P1-T15).

## Files in scope
`packages/core/src/context/**`, `packages/contracts/src/context.ts`, golden files and tests.

## Done criteria
- [ ] The output matches §7.5's shape and key order, and validates against the schema.
- [ ] Golden files, byte-identical on every run, for at least: an empty account; a P-A account (three
      holdings, one undecided, one liability); a P-C account (30 holdings, four currencies, stale
      values, archived holdings); a 200-holding account (the cap and `omitted`); a holder in one
      country with holdings from two others.
- [ ] Every fixture is at most 8 KB; a property test over random fictional accounts holds the cap.
- [ ] Facts, never advice: a test scans every template and the `answer_guide` for advice wording
      ("should", "recommend", "consider", "avoid", "don't").
- [ ] Undecided never counts in `could_use` and is always reported (`picture.undecided` and a note).
- [ ] No `Date`, no randomness, no I/O.
- [ ] Follows CONVENTIONS.md

Deviations:
- Where §7.5's example is silent: a liability's `access` is `owed` (with null reason and `until`);
  a holding with no value has `value: null`; `change` is null with nothing to compare; holdings
  carry `tags` (names, after `type`), since `ContextInput` has them and J8 asks for tag
  breakdowns; `omitted.by_type: [{type, holdings, assets, owed}]` is "the rest summarised by
  type". A fifth `answer_guide` entry points "how current and complete the figures are" at
  `picture` and `holdings[].value`. The affordability note reads "sell_first, locked and
  undecided money is excluded": sell-first money is not in `could_use` either.
- The size budget. "Holdings beyond the cap" is read as listed holdings, smallest first, joining
  `omitted`, down to none. A listed holding is about 280–360 bytes and the fixed sections about
  3.3 KB, so the 8 KB limit binds at about 14–16 holdings; exactly 25 are listed only when entries
  are small (tested).
- `meaning` is given once per type, in `types: [{type, meaning}]` before `holdings`, in the order
  the listed holdings first use each type (the Founder's decision; §7.5 rewritten to match). Types
  only in `omitted` get no entry. For "at most 8 KB for any user" two things are added: holding, type and tag names
  are cut to 64 characters with "…", and after the three steps the smallest `omitted.by_type`
  entries, then the smallest `by_currency` entries, are dropped. Only about 50 long-named types
  or about 140 currencies reach that (tested).
- Figures: shares are of assets (liabilities excluded), by each value's currency, to two decimal
  places; `pct` and `owed_to_could_use` too, half away from zero. `owed_to_could_use` is null
  when `could_use` ≤ 0. `concentration` is the ten largest positive assets before the budget
  trims it to five. A holding's `change` is `baselineChange` for that holding alone, so it is
  its contribution to `totals.change` (negative for a liability when more is owed), as J8's
  "contribution by holding". `freshness` is `empty` when no holding has a value. The baseline
  defaults to `last_month`, as §7.5's example.
- Notes, most important first: undecided (names the largest), without a value, stale (names the
  largest stale holding and its age), values in other currencies converted at their own date's
  rate, and "NetNet only knows what has been added"; an account with no holdings gets "No holdings
  have been added yet" alone. Holding names in notes are quoted (“…”) so they read as the user's
  text, not NetNet's.
- `accessBasis` is not read: the access, reason and `until` shown are the stored ones (§6.7).
  No field was added to `ContextInput`.

Open issues:
- P1-T10: `ContextInput` is used as fixed. `compileContext` filters archived holdings itself, reads
  every value (future-dated ones are ignored; old ones give the changes), needs the types of every
  holding, and needs revoked connections with `guideName` filled for `claude` and `chatgpt`.
  `accessReason` and `accessUntil` must be the holding's stored values. `chain` is the current
  `packChain`.
- P1-T15: `financialContextSchema` is the `outputSchema` (`z.toJSONSchema` works; objects are
  strict). The 8 KB is the compact JSON of `structuredContent`; the text rendering is extra. The
  tool's `baseline?` passes through as `opts.baseline`.
- A total beyond 2⁵³ minor units (e.g. ten holdings at the 10¹⁵ maximum) makes `fromMinor` throw;
  `position` already sums in plain numbers. Not reachable with real data.
- A currency under 0.5% of assets shows a share of 0.
