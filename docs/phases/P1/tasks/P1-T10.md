# P1-T10: Ledger module (P1 surface)
Status: todo
Depends on: P1-T4, P1-T6
Parallel-safe: yes

## Goal
Architecture §7.3's `Ledger`, for everything P1 needs, behind `withUser`. Each write is one
transaction with its audit rows, `data_version + 1`, its batch, its warnings and its domain events.
It is the single implementation behind both REST and MCP.

## Context
- Read: architecture §6.3 (tables), §6.6 (money and FX at write), §6.7 (accessibility applied and
  kept), §6.8 (audit and batches; undo itself is P3), §7.3 (the interface), §7.4 (duplicates;
  `record_values` 1..200, atomic). PRD J2, J3, J6. CONVENTIONS §3, §5, §9 (the Ledger row), §10, §11.
- **In scope:** `init`, `snapshot`, `context`, `listHoldings`, `getHolding`, `history`,
  `createHolding`, `updateHolding` (including archive, unarchive and a new accessibility answer),
  `deleteHolding`, `recordValues`, `updateValue`, `deleteValue`, `upsertType`, `deleteType`,
  `upsertTag`, `deleteTag`, `setPrefs`, `applyPackTypes`. **Later:** `activity`, `undo`,
  `changeBaseCurrency`, `exportAll`, `destroy` (P3); `periods` (P5). Audit rows must already carry
  everything undo will need: complete `before` and `after`, and a deleted holding's `before`
  including its values.
- **Accessibility input** (`access_answer`, the same on web and MCP): an answer id from the chain's
  question for the holding's type; or, to override a type's default, an answer id from generic's
  `other` question ("could you use it within a month?"); or `"not_sure"` (undecided); or nothing,
  for the default. `core.resolveAccess` produces the outcome, reason, until and basis, all written
  onto the holding with the pack version. A later pack version never moves them.
- **FX** comes from an injected `FxRates` (`crossRate`, P1-T8); tests use a fake. Same currency:
  `fx_source: same`, rate 1. A rate supplied by the caller: `fx_source: user` (web) or `agent`.
- **Batches:** an agent's write joins its connection's open batch if the previous write was at most
  120 s earlier (by the injected clock); a single `recordValues` call is always one batch; user
  writes have none.
- **Same date:** a value for a holding and date that already exists replaces it with the warning
  `SAME_DATE_REPLACED` (J3). Two items in one call for the same holding and date: the later item
  wins, and the earlier gets the warning.
- **Types and tags:** `init` creates one `user_type` per universal type plus the pack's types, with no
  stored name until the user renames one (§6.3). `applyPackTypes` adds missing pack types and removes
  none. `deleteType(id, moveTo?)` without `moveTo` fails with `VALIDATION_FAILED` while holdings use
  the type; with `moveTo`, they move (a merge). Tags the same with `mergeInto`.
- **Limits:** `recordValues` takes 1..200 items; names at most 120 characters; at most 20 tags per
  holding; amounts per §6.6; a value date later than the user's today + 1 day is `OUT_OF_RANGE`.
  Errors name the item index and field, so an agent can correct itself (J6).
- **Provenance on values:** `source`, `connection_id`, `batch_id`, and `client_name`, which is the
  guide name for a connection classified `claude` or `chatgpt` and the registered name otherwise
  (escaped wherever it is shown).
- **Domain events** returned in `Write.events` for the edge to `track()`: `holding_created {source,
  via?}`, `value_recorded {source}`, `value_corrected {original_source, age_at_correction}` when an
  existing value's amount, date or currency is changed.
- `createHolding` raises `LIKELY_DUPLICATE {candidates}` (from `core.likelyDuplicates`) unless
  `allowDuplicate`.

## Interface contract
- Architecture §7.3's `Ledger`, the in-scope methods, exactly.
- `packages/contracts/src/ledger.ts` (shared by REST and MCP): `CreateHolding`, `HoldingPatch`,
  `NewValue`, `ValuePatch`, `TypeInput`, `TagInput`, `PrefsPatch`, `HoldingQuery`, `HistoryQuery`,
  `Snapshot` (§7.2, values as compact tuples), `HoldingView`, `HoldingDetail`, `Series`, `Page<T>`,
  `Write<T>`, `Warning`, `DomainEvent`, `AccessAnswer`.
- `Ledger.context()` returns P1-T9's `ContextInput`; the caller runs `core.compileContext`.

## Done criteria
- [ ] Every write: one transaction; one audit row per entity touched (actor, client, connection,
      batch, action, entity, `before`, `after`); `data_version + 1`. A test enumerates the write
      methods and fails if one skips the audit.
- [ ] Atomicity: one failing item in `recordValues` writes nothing.
- [ ] Same-date replacement warns; the latest value by date drives the snapshot and the context.
- [ ] Accessibility: outcome, reason, until and basis written at create and on a new answer; a newly
      published pack version leaves them unchanged (test).
- [ ] Batches: the 120 s rule with a fake clock; one `recordValues` call is one batch; the per-user
      lock keeps grouping exact under concurrent calls.
- [ ] Duplicates: `LIKELY_DUPLICATE` with at most three candidates; `allowDuplicate` bypasses it.
- [ ] Types and tags: rename, merge and delete leave nothing orphaned.
- [ ] Every method has an isolation test: user B with A's ids gets `NOT_FOUND` and none of A's data.
- [ ] Follows CONVENTIONS.md
