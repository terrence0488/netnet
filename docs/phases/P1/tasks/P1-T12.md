# P1-T12: REST API (P1 surface)
Status: todo
Depends on: P1-T7, P1-T8, P1-T10, P1-T11
Parallel-safe: yes

## Goal
The web app reads the whole position in one call and makes every P1 write through thin REST
handlers over the Ledger, with architecture §7.2's shapes, the error mapping, the events and an
isolation case per route. The first country confirmation initialises the user's ledger.

## Context
- Read: architecture §5.1 (the web write path: events after the response), §7.2 (routes and shapes;
  writes return `{result, dataVersion, warnings}`), §7.5 (codes and statuses). CONVENTIONS §3, §9
  (the REST and MCP row), §11, §12.
- **Routes in this task:** `GET /api/snapshot`; `POST /api/holdings`; `PATCH` and `DELETE
  /api/holdings/:id`; `GET` and `POST /api/holdings/:id/values`; `PATCH` and `DELETE
  /api/values/:id`; `POST /api/types`, `PATCH` and `DELETE /api/types/:id`; the same for tags;
  `PATCH /api/prefs`. Content routes are P1-T8's, `/api/me` and `/api/geo` P1-T11's, `/api/agent/*`
  P1-T13's.
- **A handler** parses with the contract schema, calls `requireSession`, runs `withUser(userId,
  {kind: 'user'}, …)`, and maps the result. `today` is computed in `profile.time_zone`. Every write
  has `source: web`. `POST /api/holdings` requires `via` (`guided | form`). After the response,
  `Write.events` go to `track()` with the user's segment.
- **Ledger initialisation:** extend `PATCH /api/me` so the first country confirmation calls
  `Ledger.init({baseCurrency: the country's currency, pack})` (generic when the country has no pack)
  in the same request. A later change of country is P3's.
- Log the snapshot's size and value count on each request: the revisit trigger of §7.2 (1 MB gzipped
  or 20,000 values).
- `Cache-Control: private, no-store` on every response here.

## Interface contract
Architecture §7.2's rows for the routes above, exactly, with request and response schemas from
`packages/contracts/src/ledger.ts` (P1-T10). `GET /api/snapshot` honours `If-None-Match: <dataVersion>`
with `304`.

## Files in scope
`apps/api/src/http/{snapshot,holdings,values,types,tags,prefs}.ts`, `apps/api/src/http/me.ts` (the
init step only), `apps/api/test/http/**`.

## Done criteria
- [ ] Every route: a happy path, a validation error naming the fields, not-found, and an isolation
      case (user B with A's ids → `404`, none of A's marker strings in the body). A registry test
      fails when a route has no isolation case.
- [ ] Snapshot: `304` when unchanged; compact values per §7.2.
- [ ] The first country confirmation initialises the ledger once (a second call does not re-init);
      the pack's types appear in the snapshot.
- [ ] `holding_created {source: web, via}`, `value_recorded {source: web}` and `value_corrected` fire
      with the segment, and a privacy test finds no amount in any emitted event.
- [ ] Follows CONVENTIONS.md

Deviations:
- Outside the listed files: `ledger-edge.ts` (what the six routers share), `ledger/state.ts` (a `304`
  reads the version alone, in the same transaction as the snapshot it may skip), `lib/log.ts` and
  §10 (the snapshot's log line needs three numeric fields), `app.ts`, `me.test.ts` and
  `accounts-app.ts` (the new required `initLedger` dependency).
- A handler checks the session before the body, as `/api/me` does: no session is `401` whatever is
  sent. The brief lists parsing first.
- Path and query ids: a malformed one (not a ULID of the right prefix) is `400 VALIDATION_FAILED`
  naming `id`, `moveTo` or `mergeInto`; a well-formed one that is not the person's is `404`. This
  gives `DELETE` routes their validation case. `GET /api/snapshot` takes no input, so it has none.
- `POST /api/types` and `POST /api/tags` take no id, so their isolation case (B naming A's id) is
  `400` with `fields.id`, refused before any lookup; A is untouched.
- §7.2 writes `date` without `?` in `POST /api/holdings/:id/values` and `opening`; the contract
  (P1-T10) makes it optional and the Ledger dates it today in the person's time zone. The routes
  follow the contract. `POST /api/holdings` also takes the contract's `universal` in place of
  `typeId` (additive).
- Results §7.2 leaves open: `POST /api/holdings/:id/values` answers the stored `Value` (replacement
  is the `SAME_DATE_REPLACED` warning, without the list's `path`); `DELETE`s answer `result: null`;
  every write is `200`. `LIKELY_DUPLICATE`'s `candidates[].latest` is core's `{date, amountMinor,
  currency}`, minor units as in the snapshot.
- `GET /api/snapshot` also sends `ETag: "<dataVersion>"`, and `If-None-Match` matches a bare number
  (§7.2), a quoted or weak ETag, a list or `*`. Before the ledger exists it is `404 NOT_FOUND`.
- The size log line is `snapshot_sent {requestId, userId, bytes, gzipBytes, valueCount}`, written
  after the response (the gzip runs then), and only for a `200`.
- `GET /api/holdings/:id/values` caps `limit` at 200 (§7.2; the Ledger allows 500) and renames the
  Ledger's `values.cursor` to `cursor`. Request bodies are capped at 256 KB.
- `PATCH /api/me` makes the ledger only while none exists, after the profile change was accepted:
  a refused request makes nothing, a retry after a failed init makes it, and two at once make one.

Open issues:
- P1-T13 and P1-T15: the registry in `test/http/isolation.test.ts` fails until each new route of
  `app.ts` (`/api/agent/*`, `/api/auth/oauth2/*`, `/.well-known/*`, `/mcp`) is listed in
  `COVERED_ELSEWHERE` (its isolation file) or `NO_USER_DATA` (with the reason). Whichever merges
  second adds them. `renamePaths` and `writeLedger`'s tracking (`Write.events` with the segment, after
  the response) are there to reuse; MCP needs `source: agent` and snake_case paths.
- P1-T16: `GET /api/snapshot` is `404` until the first country is confirmed; send `If-None-Match`
  with the `dataVersion` held. Writes answer `{result, dataVersion, warnings}`; the type is
  `WriteResponse<T>` in `ledger-edge.ts` (not yet in contracts). `POST /api/holdings` needs `via`.
- The snapshot's `packRef` is the live pack chain, which a content publish changes without a write,
  so a `304` can keep an old `packRef` until the next write. Making the ETag cover the chain would
  change §7.2's `If-None-Match: <dataVersion>`, so it is raised, not done.
- `withUser`'s read transaction is `READ COMMITTED`: a write committing while `snapshot()` reads can
  mix two versions in one answer. Its `dataVersion` is read first, so it is never newer than the data
  and the next request refetches; `repeatable read` for reads would make it exact (P1-T10's code).
- P3: once the ledger exists, `PATCH /api/me {country}` still records a new country, and the
  snapshot's `packRef` follows it, while the base currency and pack types stay the first country's.
- One write's events are inserted concurrently, so their row order is arbitrary (they share `at`).
