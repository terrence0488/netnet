# P1-T7: Analytics — track(), the event schemas and the client events endpoint
Status: todo
Depends on: P1-T4
Parallel-safe: yes

## Goal
Every §3.5 event exists as a strict schema, and `track()` is the only way to write one, attaching
`segment`, `user_id` and `app_version` itself. The web app sends its client-side events through
`POST /api/events`. The privacy tests make a leak a failing build.

## Context
- Read: PRD §3.5 (the events, `segment`, the privacy constraint) and N9. Architecture §6.4, §7.7
  (props, who emits each, client vs server). CONVENTIONS §6, §9 (the Privacy row).
- **All 21 events are defined now.** The schema is the contract, even for events first fired in a
  later phase.
- Server events are written after the response (`waitUntil` on Vercel; awaited directly in tests).
- `segment` comes from `core.profile` (or the request context when it is already loaded), and is
  `unknown` until onboarding sets it.
- Client events accepted by `POST /api/events` are only those §7.7 marks *client*: `signup_started`,
  `session_started`, `agent_connection_started`, `insights_viewed`, `push_prompt_shown`,
  `push_prompt_result` (and `landing_view` in P4). Without a session, only `signup_started` is
  accepted. The endpoint is rate-limited per IP.
- The `visitor` hash is P4's (with the landing page); the column stays nullable.

## Interface contract
- `packages/contracts/src/events.ts`: `EventName`; `eventSchemas: Record<EventName, ZodObject>`, each
  `.strict()`, every prop an enum, a boolean or a bounded integer, named exactly as §3.5 and §7.7.
- `apps/api/src/events/track.ts`: `track(name, props, ctx: {userId?: string; segment?: Segment;
  appVersion: string})`. An unknown name or prop throws outside production and is logged and dropped
  in production.
- `POST /api/events {name, props}` → `204`; an unknown or server-only name → `400
  VALIDATION_FAILED`.
- `apps/web/src/api/events.ts`: `trackClient(name, props)` and a session tracker that fires
  `session_started` on the first activity after 30 minutes idle (P1-T14 mounts it).

## Files in scope
`packages/contracts/src/events.ts`, `apps/api/src/events/**`, `apps/api/src/http/events.ts`,
`apps/web/src/api/events.ts`, their tests.

## Done criteria
- [ ] The schemas match §7.7 exactly: names, props, enums, snake_case.
- [ ] Privacy tests: no schema has a free-text string prop (enums only); no prop name suggests an
      amount or a name (`amount`, `value`, `total`, `balance`, `name`, …); `track()` rejects extra
      props.
- [ ] `netnet_app` can insert into `analytics.event` and cannot select from it.
- [ ] `session_started` fires after 30 minutes idle and not before (fake clock).
- [ ] `POST /api/events`: accepted client events, rejected server-only events, rejected unknown
      props, the unauthenticated rule, the rate limit.
- [ ] Follows CONVENTIONS.md

Deviations:
- Outside the listed files: `db/analytics.ts` and `db/rate-limits.ts`, because only
  `apps/api/src/db/**` may touch `core` and `analytics` (CONVENTIONS §3); `lib/rate-limit.ts`,
  P1-T11's file, built now with its interface because this task needs a limit; the session seam
  (`lib/session.ts`, `lib/context.ts`); `lib/after-response.ts`; `.env.example`.
- A session-only event without a session is `400 VALIDATION_FAILED` (`fields.name`): §7.5 has no
  code for a missing session.
- Enums §7.7 leaves open: `original_source` is `web | agent | system` (the ledger's
  `value.source`); `outcome` is `ok` or one of the 11 error codes; `tool` is §7.4's 19 tools;
  `platform` is `ios | android | desktop` (§6.2). Bounds: `latency_ms` 0–900,000 (longer than any
  function runs), `age_at_correction` 0–36,500 days. `holding_created` refuses `via` with
  `source: agent`.
- `landing_view` is defined but not accepted by `POST /api/events` until P4, as the brief says.
- `app_version` is the deployed commit, 7 characters, or `dev`. Client events carry the server's,
  since a version sent by the browser would be free text.
- `track()` checks synchronously, so outside production a bad event throws at the call even inside
  `afterResponse`. The promise it returns never rejects: a failed write logs `event_write_failed`.
  `TrackContext` also accepts `undefined` for `userId` and `segment`.
- `afterResponse` reads Vercel's `waitUntil` from the runtime's request context, which is what
  `@vercel/functions` wraps, instead of adding that package and its dependency.
- The endpoint checks the body (at most 2 KB) before it touches the database, then counts it
  (60 a minute per IP), then reads the session. `props` may be left out of an event with none.

Open issues:
- First preview (P1-T18): confirm that `VERCEL_GIT_COMMIT_SHA` reaches a `--prebuilt` deployment at
  run time (otherwise every event says `dev`) and that `waitUntil` keeps the function alive for the
  write.
- `core.rate_limit` keeps one row per key per window. A later job (the daily sweep) should delete
  expired windows.
- `clientIp` trusts `x-real-ip` and `x-forwarded-for`, which only Vercel sets; elsewhere they can be
  spoofed.
- P1-T11's Origin check on state-changing requests should cover `POST /api/events`.
- PRD vs architecture: J3 says `value_corrected` fires with `source`; §3.5 and §7.7 give it
  `original_source` and `age_at_correction` only, which is what is built. M5 counts agent-written
  values "edited or undone within 48h", but `age_at_correction` is in days and `value_undone`
  carries no source, so M5's undo half cannot be limited to agent-written values.
