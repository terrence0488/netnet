browser. The end-to-end suite renders Home in a browser that can receive push as well as in one
that cannot, and the taxonomy flake is fixed at its cause.

## Report (filled by engineer)

Files changed:
- `apps/web/src/routes/home/Home.tsx`: the side column renders Position, then `<StaleNote>`, then
  `<PushCard />` (the note and the card were the other way round). `Home.module.css`: the side
  column's comment names the order. No other style change: the note and the card both keep their
  own `--space-7` top margin.
- `e2e/support.ts`: two shared init-script fixtures. `canReceivePush(page, permission)` stubs
  `PushManager` and `Notification` with the permission given. `cannotReceivePush(page)` removes
  the service worker, `PushManager` and `Notification`, which is everything `supportsPush()`
  reads.
- `e2e/home.spec.ts`: every Home test runs in two describe blocks, `without push` and `with push`
  (`default`), from one loop. The fixtures stay out of `playwright.config.ts`, so
  `pnpm test:e2e` in CI runs both blocks and the suite gains 60 runs, not a second copy of
  every spec. The event test expects `['session_started', 'push_prompt_shown:home']` where the
  card shows and `['session_started']` where it does not, each answered 204. The order is
  deterministic: the session starts when `me` lands, and the card mounts only after the snapshot
  and the pack. The stale-note test was computer-only. It now runs at 390 and 1280 px and checks
  that the card is visible (`with push`) or absent (`without push`). It also checks that the note
  sits in Position's column directly beneath it (0 to 64 px gap), and that the card is in the
  same column below the note.
- `e2e/push.spec.ts`: uses the shared fixtures in place of its own `capableBrowser` and
  `incapableBrowser`. Its capable browser had relied on the build providing a real
  `PushManager`.
- `e2e/accounts.ts`: `recordEvents` names an event's `entry` the way it already names its
  `method` (`push_prompt_shown:home`).
- `e2e/taxonomy.spec.ts`: the race below. Seven reads of captured requests now wait with
  `expect.poll`: type rename, type delete, type add (`:215`), tag add, tag rename, tag merge and
  tag delete.

The taxonomy race (`taxonomy.spec.ts:215`, "a type adds from the web, and the Add form offers
it"):
- **What the test does:** it clicks Save in the New type sheet, then immediately and
  synchronously reads `writes.bodies`. That is the list of requests a `page.on('request')`
  listener has collected.
- **What it waits for:** only the click. Playwright's `click` resolves once the mouse-up has been
  dispatched and its hit-target check has come back from the page. Click does not set
  `waitAfter`, so it waits for no network activity.
- **What the app does in between:** Save calls `create.mutate`. TanStack Query runs the
  `mutationFn` a couple of microtasks later, which calls `fetch('POST /api/types')`. While
  `page.route` is active, Playwright emits the page's `request` event only once two CDP events
  have arrived:
  - `Network.requestWillBeSent` from the renderer
  - `Fetch.requestPaused` from the browser's network interception
- **The race:** nothing orders that pair ahead of the click's own completion. When the pair
  arrives late, the check reads `[]` and the test fails. A throwaway probe ran 40 times on phone
  and measured how far the request event led the click: 3 to 27 ms. That margin is thin enough
  for a loaded run (the full suite on shared cores) to lose it.
- **The fix:** the check waits with `expect.poll`, adding no retry, skip or timeout. The same
  unguarded read appeared six more times in the file and is fixed the same way. The two Add-form
  tag tests read only after the navigation that follows the response, so they were already
  safe.

Deviations:
- The context's premise needs a correction: in this session's copy of Playwright's headless
  shell (Chromium 141), `PushManager`, `Notification` and the service worker all exist. What
  differs is `Notification.permission`: `denied` in the shell and `default` in full Chromium.
  Home's card needs `default`, which is why CI never showed it. It is also why `push.spec.ts`
  already passed in CI after overriding the permission. The fixtures do not depend on either
  build. `cannotReceivePush` removes `PushManager` and everything else the push check reads, so
  it covers the brief's "no `PushManager`". `canReceivePush` stubs `PushManager` and
  `Notification` at `default`. I could not check the newer shell that CI installs for
  Playwright 1.63, because `playwright install` is off limits here.
