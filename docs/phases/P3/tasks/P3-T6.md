# P3-T6: Web push — channel, devices and asking

Status: todo
Depends on: P3-T3 (both extend Settings and sign-out; ordering only)
Parallel-safe: yes

## Goal

Where the browser can receive push, the person is asked once and gently, the
reminder arrives on every device they turned on, and every device in the list
is one they still use.

## Context

- PRD J12 (asking, Settings → Notifications, lifecycle) is the contract;
  architecture §7.10 ("How web push works here") and §7.2 (the endpoints API)
  are the spec.
- P3-T5 owns the reminder timing, the `reminder.comeback` message and the
  email fallback. This task owns the `webpush` channel, the endpoint table and
  API, the service worker, the Home card and Settings → Notifications.
- Founder item F19: `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`
  must be set before anything push-related works.
- Capability rule: "can receive push" is decided in the browser (a service
  worker, `PushManager` — or Declarative Web Push — and `Notification`). Where
  one is missing, including an iPhone or iPad in a Safari tab, no push option
  appears anywhere and there is no Home Screen how-to.

## Interface contract

- `core.notification_endpoint(id, user_id, channel 'webpush', endpoint,
  keys {p256dh, auth}, platform, device_label, created_at, last_seen_at,
  last_success_at, failure_count, revoked_at)`. Active = not revoked.
- `GET /api/notifications/prefs` → `{reminders, email, emailVerified,
  devices: [{id, label, platform, lastSeenAt}]}` (active only).
  `PATCH /api/notifications/prefs {reminders?, email?}` applies at once.
- `GET /api/notifications/vapid-key` → `{publicKey}`.
  `POST /api/notifications/endpoints {endpoint, keys, platform, deviceLabel}`
  → `{id}`, idempotent per endpoint URL (re-activates a revoked row), fires
  `push_enabled {platform}`.
  `PUT /api/notifications/endpoints/:id {endpoint, keys}` → `204` (updates
  `last_seen_at` and rotated subscriptions) or `404` (the app unsubscribes
  locally and shows the switch off).
  `DELETE /api/notifications/endpoints/:id?by=user|signout` fires
  `push_disabled {platform, by}`.
- The `webpush` channel: payload `{"web_push": 8030, "notification": {title,
  body, navigate}}`, encrypted per device (aes128gcm, `web-push` lib), VAPID
  signed, `urgency: normal`, TTL = time left until 21:00 in the person's zone.
  `404`/`410` or five failures in a row revokes the endpoint (`push_disabled
  {by: browser}`).
- `/app/sw.js` handles `push` and `notificationclick` only — no `fetch`
  handler, caches nothing. `notificationclick` focuses or opens `/app/?r=‹token›`.
- Home card: first picture (≥ 1 holding), capable browser, device undecided →
  one quiet card below the Position ledger: "Want a gentle nudge on this device
  if you haven't looked in a while?", **Turn on** / **Not now**. Never during
  sign-up or the basics. Not-now state stays on the device (`localStorage`):
  first hides 30 days, second hides for good. Fires `push_prompt_shown
  {entry: home}` and `push_prompt_result`.
- Settings → Notifications: **Reminders** on/off (default on; off = nothing by
  any channel), **Notifications on this device** on/off (capable browsers
  only), **Email reminders** on/off with the one line that email is used only
  when no device has notifications on, **Other devices** ("Android · Chrome",
  last used) each with **Remove**, and the security email listed as "Always".
  Permission is requested only inside the tap that turns push on; Denied leaves
  the switch off with a one-line pointer to the browser/phone settings and
  never re-asks on its own.
- Sign-out (P3-T3's flow): `unsubscribe()`, then `DELETE ?by=signout` for this
  device. After signing in again the switch turns push back on without a
  prompt. Account deletion removes every endpoint with no `push_disabled`.
