# P3-T13: Account deletion leaves nothing behind; the export survives Safari

Status: todo
Depends on: none
Parallel-safe: yes

## Goal

Deleting an account erases everything at once and nothing comes back for the erased id. The
export's download is not cancelled by Safari.

## Context

- Test report issue 3: after `DELETE /api/account`, one `core.profile` row and one
  `core.reminder_state` row exist again for the deleted id. The after-response hook
  `touchCheckedOnSession` (`apps/api/src/auth/touch-checked.ts`) runs for the deletion request
  itself and calls `touchChecked` (`apps/api/src/db/reminders.ts`), which ensures a profile and
  upserts the reminder row. Nothing is sent to that id, because no address remains, but erasure
  is incomplete and orphans pile up.
- Architecture §8 (Deletion: ledger rows, identity, sessions, grants, endpoints and reminder state,
  events re-keyed), §7.10 (`touchChecked`), plan §P3 checkpoint 3.
- Prefer a guarantee from the database over a remembered check (decisions.md, isolation by RLS).
  If `core.profile` and `core.reminder_state` can carry a foreign key to the identity table with
  `ON DELETE CASCADE`, the database then refuses an orphan, including one from a request that
  races the deletion. Otherwise the hook must skip a user who no longer exists, in the same
  statement that writes.
- Test report issue 14: the export revokes its blob URL straight after `click()`. Safari has been
  known to cancel downloads like that. The Founder's manual check 9 tries it on an iPhone.

## Interface contract

- No API change. `DELETE /api/account` still answers `{erasedWithinDays: 30}`.
- After it, no row in `core`, `ledger` or identity carries the erased id. Analytics events stay,
  re-keyed, as now.
- The web export revokes its object URL only after the download has started (a later task, not
  the same tick as `click()`).

## Files in scope

## Report (filled by engineer)

Files changed:
- `apps/api/src/db/schema.ts` + `migrations/0008_user_foreign_keys.sql` (+ snapshot, journal):
  every `core` table keyed by a user id (`profile`, `reminder_state`, `agent_connection`,
  `notification_endpoint`, `connection_attempt`) references `core.user(id)` with `ON DELETE
  CASCADE`. The migration first deletes the rows earlier releases left for ids no account holds
  (the orphan profiles and reminder rows, and the revoked connections P3-T4 kept), then adds the
  keys, so it applies to production as it is. The tables are owned by `netnet_owner` like the user
  table; the cascade runs as the owner, so `netnet_app` needs no new grant.
- `apps/api/src/db/reminders.ts`: `touchChecked` makes no profile (it reads the profile's time
  zone, UTC without one) and its upsert takes its row from `core.user`, so an id no account holds
  gets nothing in the statement that writes. A write that waited on the deletion's locks and lost
  its commit is refused by the key; that one error (SQLSTATE `23503`) ends it quietly instead of
  logging `after_response_failed`. `setRemindersEnabled` and `setEmailReminders` (also "make the
  row if missing") write the same way.
- `apps/api/src/db/profiles.ts`: `createProfile` makes a profile only for an account that exists;
  `ensureProfile` throws `UNAUTHENTICATED` (was a plain `Error`, a 500) when none could be made,
  which now means the account is gone. Without this, the key would turn GET `/api/me` for a
  session that outlived its account from 401 into 500. `deleteUser`'s comment lists the cascade.
- `apps/api/src/db/client.ts`: `isForeignKeyViolation()` (walks Drizzle's `cause` chain).
- `apps/api/src/db/seed.ts`: the demo person gets a `core.user` row first (no credential, so no
  way to sign in), or `db:seed` would be refused by the keys.
- `apps/api/src/http/account.ts`: comments only. The steps and their order are unchanged; the
  explicit deletes before `deleteUser` are now also done by the cascade, which catches a row a
  racing request wrote after them.
- `apps/web/src/api/export.ts`: the object URL is revoked `EXPORT_URL_LIFETIME_MS` (60 s) after
  the click, by `setTimeout`, never in the click's task. Otherwise the export is unchanged.
- Events (`db/analytics.ts`, `events/track.ts`, `http/account.ts`): an event for a verified user
  goes through `insertAccountEvent`, `INSERT … SELECT … FROM core."user" … FOR KEY SHARE`, so it
  is written only while the account exists and either commits before the deletion's `delete`
  (then `rekeyEvents`, after it, re-keys the event) or finds no account. `account_deleted` goes on
  `TrackContext.rekeyedUserId`, the random id, through the plain insert. Tests:
  `account-deletion.test.ts` holds the deletion before its commit while a `POST /api/events`
  write waits, and holds an event write while the deletion waits; `events.test.ts` and
  `track.test.ts` cover both inserts and the new context field. `e2e/delete-account.spec.ts`
  finds its own `account_deleted` by the re-keyed id of one of the account's events, not by
  "after this event id", which a parallel worker's deletion broke.
- Tests:
  - `test/support/erasure.ts` (new): `rowsCarrying(owner, id)` searches every text column of every
    table in `core` and `ledger` (from the catalog, so new tables and columns are covered) for the
    id. This includes identity, sessions, grants, `verification.value` (reset tokens) and every
    ledger table.
  - `test/auth/account-deletion.test.ts`: through a real Better Auth cookie session, with the
    after-response hook wired as in app.ts. (1) A stocked account (a ledger with a row in every
    ledger table, two connections, all grants, a device, an attempt, a reset token) leaves no
    row anywhere once everything has settled, and nothing logs `after_response_failed`. Before
    the fix it found `core.profile` 1, `core.reminder_state` 1 and `core.agent_connection` 2.
    (2) The race: the deletion is held just before its commit, a GET `/api/me` on the same session
    answers 200, and its `touchChecked` waits on the deletion's locks (checked in
    `pg_stat_activity`). Then the commit is released. Nothing is re-created and nothing is logged.
    It failed before the fix, and with the key's refusal rethrown it fails on the log, so it does
    reach the race path. (3) A catalog test: every `core` table with a `user_id` column has a
    key to `core.user` with cascade (set null for the shared `oauth_client`).
  - `test/auth/migration.test.ts` (new): 0008 over 0000–0007 with a kept account and an erased
    id's rows in all five tables. Orphans go, the account's rows stay, a new orphan is refused,
    and deleting the account deletes its rows. It also applies to an empty database.
  - `test/reminders/touch.test.ts`: a missing reminder row is made for an account (in its time
    zone, Pacific/Kiritimati), with no profile made; an id no account holds gets nothing from
    `touchChecked` or either switch; the database refuses such rows itself; the switches still
    make a missing row for an account.
  - `test/http/account.test.ts`: connections are now deleted with the account (expected 0, was 2
    "revoked, not deleted"). After the deletion, a header session that outlived the account gets
    401 on GET `/api/snapshot` (was 404, by way of a re-created profile), and `rowsCarrying` finds
    nothing.
  - Fixtures that wrote user-keyed rows for ids with no account: `ensureAccount()` in
    `test/isolation/harness.ts`, used by `seedUsers`, `ledgerSuite.connect` and
    `test/events/events.test.ts`.
  - `apps/web/src/api/export.test.ts`: with fake timers, nothing is revoked during `click()`, in
    the next task, or before `EXPORT_URL_LIFETIME_MS`, then exactly the clicked URL is. It fails
    on the old code.

Deviations:
- The keys cover five tables, not only `profile` and `reminder_state`. The contract says no
  `core` row may carry the erased id, and P3-T4 kept the revoked `agent_connection` rows. They are
  now deleted with the account. The next agent call is still refused: the MCP route and
  `isConnectionActive` treat a missing connection as revoked. Endpoints and attempts were already
  deleted; the keys also cover a racing write to them.
- Files beyond the brief's list, each forced by the key: `db/schema.ts`, `db/profiles.ts` (see
  above: otherwise a stale session becomes a 500), `db/client.ts`, `db/seed.ts`, and test fixtures.
- A session that outlives its account (only possible while a request races the deletion: the
  cookie session dies with the account) now gets 401 `UNAUTHENTICATED` from ledger routes too,
  where it used to get 404 after re-creating a profile. No contract change; `DELETE /api/account`
  still answers `{erasedWithinDays: 30}`.
- The revoke waits 60 s, not one tick: iOS Safari may ask before it saves, and a minute holds a
  small blob.

Open issues:
- Migration numbering: P3-T11 and P3-T12 each add a migration too. Whichever merges after another
  must regenerate its own as the next number (the journal's `when` must also increase).
- Docs not edited (outside the brief's scope), for the manager:
  - Architecture §8 (Deletion) could say that connections are deleted with the account.
  - §6.2 could state the user-id keys with cascade.
  - §7.10 describes `touchChecked` as one `UPDATE`, but the code, before and after this task, is
    an upsert that makes a missing row (the repair for a failed sign-up hook).
  - `decisions.md` may want the key decision.
- The ledger has no database guarantee: `ledger.ledger_state` has no key to `core.user`. Only
  `Ledger.init` (the first country confirmation, PATCH `/api/me`) creates a ledger, so a PATCH
  that read the profile before the deletion committed and ran `init` after it could leave a ledger
  for the erased id. That window is very narrow. Closing it would take a cross-schema key from
  `ledger_state` to `core.user`, which every ledger fixture would then need.
- Other writes that lose the race to the deletion's commit (`saveEndpoint`, `insertAttempt`,
  `insertConnection`) are refused by the key, and that request answers 500. They leave no orphan.
- For P3-T18 (the 500 on GET `/api/me`):
  - The lead's mechanism is gone. `touchChecked` was the only after-response writer of
    `core.profile`, and it no longer writes one.
  - I could not build a sequence in which it caused a 500. Both sides did insert … on conflict do
    nothing, then read, in READ COMMITTED.
  - `ensureProfile`'s only 500 was its plain `Error` when no profile could be made, which needs
    the account gone. That case is now a 401.
  - Side effect now fixed: the first request after sign-up could make the profile in UTC before
    sign-up's own hook made it in the browser's time zone.
  - Unrelated to `/api/me`, but worth a look: for a route that never resolved the session,
    `touchCheckedOnSession` resolves it after the response. If Better Auth then refreshes the
    session (once a day), `sessionFromCookie` calls `c.header('Set-Cookie')` on a finalized
    context. Hono 4.13 then rebuilds `c.res` from the body already handed to the server.
