# P3-T1: Activity log and undo (Ledger, REST, MCP)

Status: todo
Depends on: none
Parallel-safe: yes

## Goal

Every change an agent or the person made is visible and reversible through one
implementation: paged activity reads and undo of a single entry or a whole agent
turn, over REST and MCP, with conflicts that name the blocking change.

## Context

- Architecture §6.8 (Audit, batches and undo) is the spec: one transaction per
  write with audit rows and `data_version + 1`; a connection's writes join one
  batch while each follows the previous by ≤ 120 s; a single `record_values`
  call is always one batch.
- Architecture §7.3 (`Ledger.activity`, `Ledger.undo`), §7.2 (the
  `/api/activity*` routes), §7.4 (`list_activity`, `undo`), §7.5
  (`UNDO_CONFLICT`), §7.7 (`value_undone`, `value_corrected`).
- P1 wrote the audit and batch rows on every write (N3); this task reads and
  reverts them. If batch rows are missing anywhere in the write path, add the
  grouping inside that path (same transaction) rather than working around it.
- Revocation is already logged by P1; this task surfaces it in the log.

## Interface contract

```ts
// Ledger (apps/api/src/ledger). All inside withUser; undo takes the write lock.
activity(p: PageReq & { batchId?: string }): Promise<Page<AuditEntry>>;
undo(t: { entryId: string } | { batchId: string }): Promise<Write<UndoResult>>;
```

- `GET /api/activity?cursor&limit≤100` → audit entries, newest first, grouped
  by batch (one agent turn). `GET /api/activity?batchId=` filters to one turn.
- `POST /api/activity/:entryId/undo` and
  `POST /api/activity/batches/:batchId/undo` → `{result, dataVersion,
  warnings}`. Undo of an entry restores `before` exactly, and only if the
  entity is still at the entry's `after` (by `row_version`); otherwise `409
  UNDO_CONFLICT {blockers: [{entry_id, action, at}]}` naming the later change
  to undo first. Undo of a batch reverts every not-yet-undone entry, newest
  first, in one transaction, all or nothing. Each undo is itself an audit entry
  (`undoes`, `undone_by`), so it can be undone too.
- MCP `list_activity {cursor?, limit≤100, batch_id?}` and `undo {entry_id |
  batch_id}` (write, non-destructive hint false). Same semantics, snake_case.
- `value_undone` fires on every undo of a value. An undo of an agent-written
  value keeps the M5 attribution readable (the undone entry's `original_source:
  agent` stays on the audit trail).
- Revocation entries read as "Agent disconnected" with client name and time.
