# P3-T21: Failure logs name their cause, and a sign-out logs nothing

Status: todo
Depends on: none
Parallel-safe: yes

## Goal

Every failure log carries the class of the error behind it, as architecture §10 requires. With
that in place, the failure every sign-out logs is root-caused and fixed.

## Context

- Test report issue 3: every `POST /api/auth/sign-out` logs `{"event":"after_response_failed",
  "route":"POST /api/auth/sign-out","errorCode":"INTERNAL"}`, four times out of four, and Postgres
  logged no error. The failing task is `touchCheckedOnSession`
  (`apps/api/src/auth/touch-checked.ts`). After the response it calls `c.var.session()`, which
  reads the session the sign-out has just removed. Nothing is lost: to sign out, the person opened
  Settings, and that request already counted as checking NetNet (§7.10). But production would log
  a failure on every sign-out with no way to read why.
- **A lead (P3-T13's report, unverified):** when a route has not resolved the session, the touch
  resolves it after the response. `sessionFromCookie` (`apps/api/src/auth/session.ts`) then copies
  Better Auth's `Set-Cookie` headers onto a finalized context with `c.header`. For a removed
  session, Better Auth answers with headers that clear the cookie. For a session due its daily
  refresh, it answers with a refreshed cookie, which then never reaches the browser. Better Auth
  1.7.7's `getSession` takes `query: { disableRefresh: true }`.
- Architecture §10: logs carry an unexpected error's class (its name and Postgres SQLSTATE, never
  its message). P3-T18 added `errorClass()` (`apps/api/src/lib/log.ts`) and used it in
  `request_failed` only. Its report lists the failure logs that still drop the cause:
  `after_response_failed` (`lib/after-response.ts`), `tool_failed` (`mcp/errors.ts`),
  `auth_task_failed`, `profile_create_failed` and `auth_error` (`auth/auth.ts`), and
  `agent_task_failed` (`auth/agent.ts`). Better Auth's logger receives the error but logs only
  `auth_error`. `inBackground`'s failure callback takes no argument, so it cannot pass the error
  on.
- §7.10 stands. The touch counts a request whose session is still there after the response. A
  sign-out's session is not.

## Interface contract

- `inBackground(task, onFailure: (error: unknown) => void)`: the callback receives the rejection.
- Each failure log listed above spreads `errorClass(error)` beside its `errorCode`. The log
  whitelist already refuses messages, SQL and values, and none is added.
- Reading the session after the response never writes to the response, and never refreshes a
  session whose new cookie could not reach the browser. The next request that reads the session
  in the foreground refreshes it as now.
- No REST, MCP or schema change.

## Files in scope

- `apps/api/src/lib/{after-response,log,session}.ts`, `apps/api/src/mcp/errors.ts`
- `apps/api/src/auth/{auth,agent,session,touch-checked}.ts`
- Their unit tests, and `apps/api/test/**`

## Done criteria

- [ ] Every failure log listed carries `errorName`, and `pgCode` where the error has one, from the
      error that caused it. Unit tests show this and that no line carries a message, SQL or a
      value
- [ ] The report names the sign-out failure's cause, read from the new log, and the fix removes
      it: an integration test signs in, signs out and finds no `after_response_failed`
- [ ] A route that does not read the session still restarts the person's clock after its response,
      and a session due its refresh is not refreshed after the response (tests on both)
- [ ] Follows CONVENTIONS.md
