# P3-T21: Failure logs name their cause, and a sign-out logs nothing

Status: todo
Depends on: none
Parallel-safe: yes

## Goal

Every failure log carries the class of the error behind it, as architecture §10 requires. With
that in place, the failure every sign-out logs is root-caused and fixed.

## Context

- Test report issue 3: every `POST /api/auth/sign-out` logs `{"event":"after_response_failed",
  "route":"POST /api/auth/sign-out","errorCode":"INTERNAL"}`, four times out of four, and Postgres
  logged no error. The failing task is `touchCheckedOnSession`
  (`apps/api/src/auth/touch-checked.ts`). After the response it calls `c.var.session()`, which
  reads the session the sign-out has just removed. Nothing is lost: to sign out, the person opened
  Settings, and that request already counted as checking NetNet (§7.10). But production would log
  a failure on every sign-out with no way to read why.
- **A lead (P3-T13's report, unverified):** when a route has not resolved the session, the touch
  resolves it after the response. `sessionFromCookie` (`apps/api/src/auth/session.ts`) then copies
  Better Auth's `Set-Cookie` headers onto a finalized context with `c.header`. For a removed
  session, Better Auth answers with headers that clear the cookie. For a session due its daily
  refresh, it answers with a refreshed cookie, which then never reaches the browser. Better Auth
  1.7.7's `getSession` takes `query: { disableRefresh: true }`.
- Architecture §10: logs carry an unexpected error's class (its name and Postgres SQLSTATE, never
  its message). P3-T18 added `errorClass()` (`apps/api/src/lib/log.ts`) and used it in
  `request_failed` only. Its report lists the failure logs that still drop the cause:
  `after_response_failed` (`lib/after-response.ts`), `tool_failed` (`mcp/errors.ts`),
  `auth_task_failed`, `profile_create_failed` and `auth_error` (`auth/auth.ts`), and
  `agent_task_failed` (`auth/agent.ts`). Better Auth's logger receives the error but logs only
  `auth_error`. `inBackground`'s failure callback takes no argument, so it cannot pass the error
  on.
- §7.10 stands. The touch counts a request whose session is still there after the response. A
  sign-out's session is not.

## Interface contract

- `inBackground(task, onFailure: (error: unknown) => void)`: the callback receives the rejection.
- Each failure log listed above spreads `errorClass(error)` beside its `errorCode`. The log
  whitelist already refuses messages, SQL and values, and none is added.
- Reading the session after the response never writes to the response, and never refreshes a
  session whose new cookie could not reach the browser. The next request that reads the session
  in the foreground refreshes it as now.
- No REST, MCP or schema change.

## Files in scope

- `apps/api/src/lib/{after-response,log,session}.ts`, `apps/api/src/mcp/errors.ts`
- `apps/api/src/auth/{auth,agent,session,touch-checked}.ts`
- Their unit tests, and `apps/api/test/**`

## Done criteria

- [ ] Every failure log listed carries `errorName`, and `pgCode` where the error has one, from the
      error that caused it. Unit tests show this and that no line carries a message, SQL or a
      value
- [ ] The report names the sign-out failure's cause, read from the new log, and the fix removes
      it: an integration test signs in, signs out and finds no `after_response_failed`
- [ ] A route that does not read the session still restarts the person's clock after its response,
      and a session due its refresh is not refreshed after the response (tests on both)
- [ ] Follows CONVENTIONS.md

## Report (filled by engineer)

The sign-out failure's cause, as the new log read it:
- With the error's class in place, the integration test's sign-out logged
  `{"event":"after_response_failed","route":"POST /api/auth/sign-out","errorCode":"INTERNAL",
  "errorName":"TypeError"}`. It did so only once the test had read the response body, as a server
  does when it streams the body to the browser. Without the body read, nothing failed. The
  error's stack, printed once by hand and not committed, ran from `sessionFromCookie`'s
  `c.header('Set-Cookie', …)` (`auth/session.ts`) through Hono's `Context.header` to undici's
  `new Response`: "Response body object should not be disturbed or locked".
- So P3-T13's lead holds. The sign-out route never reads the session, so `touchCheckedOnSession`
  reads it first, after the response. Better Auth finds the session gone and answers with headers
  that clear its cookie. Copying them onto the finalized context makes Hono rebuild the response
  around a body that has already been sent, and that throws. No query fails, which is why Postgres
  logged nothing. A session due its daily refresh went the same way: it was refreshed in the
  database after the response, and its new cookie never reached the browser.
- The same evidence from the real server: the built app (`e2e/server.ts` over the bundled
  function) took four rounds of sign-in, `GET /api/geo` and sign-out. With P3-T21's first commit
  (the error's class in the logs, no fix) it logged four `after_response_failed` lines, each with
  `errorName: TypeError`, as in the test report. With the fix it logged none.

Files changed:
- `apps/api/src/lib/after-response.ts` (+ test): `inBackground`'s failure callback receives the
  rejection, and `after_response_failed` spreads `errorClass(error)` beside its `errorCode`.
- `apps/api/src/mcp/errors.ts` (+ new `errors.test.ts`): `tool_failed` spreads `errorClass(error)`.
- `apps/api/src/auth/auth.ts` (+ test): `profile_create_failed` spreads the class of the error its
  `catch` receives. `auth_task_failed` is `authBackground`, exported so its test can call it.
  Better Auth's logger is `logAuthError`: at level `error`, it logs `auth_error` with the class of
  the first `Error` among the message and its arguments, and never their text. Better Auth reports
  some errors as text alone ("Failed to create session"), and those lines carry no class.
- `apps/api/src/auth/agent.ts` (+ new `agent.test.ts`): `agent_task_failed` is `agentBackground`,
  exported likewise, and spreads `errorClass(error)`.
- `apps/api/src/auth/session.ts` (+ test): a read once the response is final (`c.finalized`, which
  Hono sets as soon as the route has answered, so it is true wherever a middleware reads after
  `await next()`) asks Better Auth's `getSession` for `query: { disableRefresh: true }` and copies
  no header to the response. A read during the request is unchanged: it refreshes a session due
  its refresh and sends the new cookie. The answer-to-user mapping moved into `userOf()`.
- `apps/api/src/auth/touch-checked.ts`: its comment states the rule. It counts a request whose
  session is still there after the response, which a sign-out's is not. No code change.
- `apps/api/test/support/failures.ts` (new): fictional failures for the log tests. One is a
  `DrizzleQueryError` around a `pg` `DatabaseError`, carrying SQL, parameters, a detail and a
  message. The other is a plain `TypeError` whose message names a holding, an amount and an
  email. The file also has the pattern for any of their text (`LEAKS`), and `captureLog()`, which
  keeps stdout and stderr as written.
- `apps/api/test/reminders/touch.test.ts`: the session read after the response (three tests,
  below).
- `apps/api/test/auth/accounts.test.ts`: a test of `profile_create_failed` from a real Postgres
  error.

Deviations:
- `profile_create_failed` is tested by an integration test, not a unit test. It is logged inside
  Better Auth's user hook, which runs only with a database. The real Postgres error shows the
  SQLSTATE end to end.
- `authBackground`, `agentBackground` and `logAuthError` are new exports, so each failure log can
  be tested without building the running app's Better Auth or agent service.

Open issues:
- The rule keys on `c.finalized`. A read started during the request but not awaited before the
  route answers would decide before finalization and write after it. No route reads that way:
  each awaits `c.var.session()`, directly or through `requireSession`, before answering.
- `auth_error` names a class only when Better Auth hands it an `Error`. Its text-only error logs
  still say only that something failed.
