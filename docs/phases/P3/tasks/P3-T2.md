# P3-T2: The Activity screen

Status: done
Depends on: P3-T1
Parallel-safe: yes

## Goal

The person sees everything an agent or they themselves changed, newest first
and grouped by agent turn, and can undo one entry or a whole turn from the
screen.

## Context

- PRD J7 is the contract; P3-T1 provides `GET /api/activity` (newest first,
  grouped by batch) and the two undo endpoints, including `UNDO_CONFLICT`.
- Web changes read in the same log as agent changes. Revocation reads as "Agent
  disconnected" with client name and time (P3-T1).
- `docs/02-prototype/design-system.md` is the visual spec (CONVENTIONS §13):
  tokens only, one figure one place, 44 px touch targets, `aria-disabled`,
  reduced motion honoured.

## Interface contract

- New route under `/app` (Activity). Consumes only P3-T1's REST: list with
  cursor paging (`limit≤100`), undo entry, undo batch.
- Each entry shows what changed, old → new, which client did it and when. Each
  agent turn groups with one "Undo these N changes" control; each entry has its
  own Undo. An `UNDO_CONFLICT` names the later change and offers to undo it
  first, in plain language, no codes on screen.
- Empty state when nothing has changed yet. Totals recompute after an undo
  (refetch `snapshot` with the returned `dataVersion`).
- No new analytics events; undoing an agent-written value is already covered by
  the server's `value_undone`.

## Report (filled by engineer)

Files changed:
- `apps/web/src/api/activity.ts` (new): typed client over T1's REST —
  `GET /api/activity` as an infinite query (`limit=50 ≤ 100`), the two undo
  POSTs as mutations. The undo response's `dataVersion` moves the snapshot on
  through the app's mutation cache, so totals recompute; the log invalidates
  so the undo entry reads at the top.
- `apps/web/src/routes/activity/Activity.tsx` + `Activity.module.css` (new):
  the `/app/activity` screen — newest-first log, each agent turn its own card
  with one "Undo these N changes" control, each standing entry its own Undo,
  old → new beneath the summary (values, renames, short preference changes),
  actor/client and the timestamp, the empty state, "Show older changes"
  paging. A conflict names the newer change from the loaded log and offers to
  undo it first; failures read in plain language, never a code or an id.
- `apps/web/src/routes/activity/activity.ts` (new): grouping, old → new,
  actor/timestamp readings, conflict parsing and copy.
- `apps/web/src/app/routes.tsx`, `apps/web/src/app/nav.ts`: the route and its
  nav entry, in tabs and sidebar.
- Tests: `apps/web/src/routes/activity/activity.test.ts` (helpers),

Deviations:
- Activity is in both tabs and sidebar, not sidebar-only as `nav.ts`
  suggested: mobile is primary and no other phone entry point (Home icon,
  Agent link) is in this task's scope.
- An entry that already stands undone shows no Undo (its summary reads
  "(undone)"); the way back is the undo entry's own Undo. Undoing it again
  could only conflict with its own undo.
- A turn's control counts only entries that still stand, and hides when none
  do; a lone batch entry renders without a turn header.
- Entries T1 refuses (a revocation, the ledger's creation) keep their Undo
  as briefed; the refusal reads "This change can't be undone." with the next
  step, no codes.
- Wiring outside the listed scope, required by "a new route under /app":
  `app/routes.tsx`, `app/nav.ts`, and `app/nav.test.ts` (whose hypothetical
  sidebar-only example is now Insights, P5's entry).

Open issues:

  session for a pre-existing environmental reason: it visits screens that
  fetch the unmocked `GET /api/content/current`, which answers 500 without
  `DATABASE_URL` (reproduced with curl, no browser; API code this task never
  touched). It should pass in CI with a database. The DB-backed specs
  (`auth`, `onboarding`, `providers`, `agent-connect`, part of `agent`) could
  not run here for the same reason.
- Suggested manual check: a real undo against seeded data, and the screen in
  dark mode (tokens only, both themes authored, but E2E asserts light).
