# P3-T18: The intermittent 500 on `GET /api/me` — diagnosable, then fixed

Status: done
Depends on: none
Parallel-safe: yes

## Goal

An unexpected error names its cause wherever it happens, without leaking data. With that in place,
the intermittent 500 on `GET /api/me` is caught and fixed, or shown not to recur.

## Context

- Test report issue 10: one 500 on `GET /api/me` right after confirming a country, in one full
  integration run (`apps/api/test/auth/accounts.test.ts`, "lets an unverified person use the
  app"). It did not reproduce in 3 isolated runs or in 40 concurrent sign-up → confirm → read
  attempts.
- `apps/api/src/lib/error-handler.ts` logs `request_failed` with no cause and sends the error only
  to Sentry. Local runs and CI have no Sentry, so the cause is lost.
- Architecture §10, rewritten: logs carry an unexpected error's class (its name and Postgres
  SQLSTATE, never its message). Where no Sentry DSN is set (local runs and tests, never
  production), the stack also goes to stderr.
- An unverified lead worth checking first: after-response work from the previous request (the
  `touchChecked` hook ensures a profile) racing the next request's read of the profile.

## Interface contract

- `internal()` in `error-handler.ts` logs `errorName` and `pgCode` (new whitelisted fields in
  `apps/api/src/lib/log.ts`). Neither ever carries a message, SQL or a value.
- With no `SENTRY_DSN`, `internal()` also writes the error's stack to stderr. With one, nothing
  extra is written.
- No API change.

## Files in scope

- `apps/api/src/lib/{error-handler,log}.ts` and their tests
- Whatever the cause turns out to be, for its fix only
- `apps/api/test/**`

## Done criteria

- [x] An unexpected error logs its class and SQLSTATE, and its stack reaches stderr only when no
      Sentry DSN is set (unit tests on both)
- [x] The accounts suite has run repeatedly (at least 20 full runs, in CI's parallelism), and the
      report gives the count and what was seen
- [x] If the 500 recurred, its cause is fixed with a regression test. If not, the report says so
      and the logging stays, so the next one names its cause
- [x] Follows CONVENTIONS.md

## Report (filled by engineer)

Files changed:
- `apps/api/src/lib/log.ts` (+ test): `errorName` and `pgCode` are whitelisted, each only in its
  exact form: an identifier of at most 64 characters, and a five-character SQLSTATE (digits and
  capitals). Any other value is refused outside production and dropped in production, like an
  unknown field. `errorClass(error)` derives both: the name of the error's class (its
  constructor's, so Drizzle's wrapper reads `DrizzleQueryError`, not its `name`, `Error`), and the
  first SQLSTATE along the `cause` chain (up to 8 deep) from an error that also has a `severity`,
  as the Postgres driver's errors do, so a system code such as `EPIPE` is never taken for one. It
  never throws, even on a hostile error.
- `apps/api/src/lib/error-handler.ts` (+ test): `internal()` adds `errorClass(err)` to
  `request_failed`. With no `SENTRY_DSN`, and outside production, it also writes the error to
  stderr (`console.error(err)`: the stack, the cause chain and Drizzle's query). With a DSN,
  nothing extra is written.
- `apps/api/src/http/notifications.test.ts`: the VAPID test captured every console call as a log
  line; it now keeps the log's lines only, as the stack is written as the error itself.

Tests run / results:
- `pnpm lint`, `pnpm typecheck`, `pnpm content:check` (8 documents): pass. `pnpm db:generate`:
  no schema changes.
- `pnpm test`: 129 files, 1484 tests pass (incl. the N10 deny-list scan). New: 20 in
  `log.test.ts` (the two fields; each rejecting a message, a holding name with an amount, an
  email, SQL, an overlong name, an empty one, and a SQLSTATE of the wrong length, padding or case;

  and SQLSTATE logged with no message, SQL or value in any log line; the stack on stderr without

- The accounts suite (`apps/api/test/auth/accounts.test.ts`, 29 tests, one file, as CI runs it
  with `fileParallelism: false`): **45 full runs**, all 29 tests passing every time, with no
  `request_failed`, `after_response_failed` or `auth_error` line and nothing on stderr: 25 runs
  before the machine restarted mid-task (their saved logs verified afterwards) and 20 after it, on

- `pnpm test:int` (56 files, 741 tests), 3 full runs: the accounts suite passed in all three. The
  third run passed whole. The first two each timed out (5 s) on the same two tests,
  `test/mcp/lifecycle.test.ts` › rate limits (120 MCP calls in a test). That happened while lint,
  typecheck and `pnpm test` ran beside them on four shared cores (load average 9.7). The file
  passed twice on its own, and whole in the third run. The new logging named the one 500 of those
  runs: a `POST /mcp` from a timed-out test, still running after the file closed its pool
  (`DrizzleQueryError`, caused by "Cannot use a pool after calling end on the pool"). It was a
  consequence of the timeout, not a defect.
- The lead, by hand: a scratch stress test (not committed) ran 510 requests against the accounts
  app. They were 60 rounds of sign-up, `PATCH /api/me {country}` and two `GET /api/me` with
  nothing settled in between; 60 rounds of two `GET /api/me` racing two direct `touchChecked`
  calls on a person whose profile had been deleted; and 30 rounds of five concurrent PATCH and
  GET requests for one person. All were 200, with no `after_response_failed`.
- Finding: the 500 did not recur in 45 runs of the suite or 3 full integration runs, so no cause
  is fixed and nothing depends on P3-T13. The logging stays, so the next one names its cause.
- The lead does not produce a 500, by reasoning and by the stress test above:
  - `touchChecked` runs after the response through `afterResponse`. A failure there is caught and
    logged as `after_response_failed`, so it cannot change any response's status.
  - `ensureProfile` runs each statement on its own on the pool (read committed, a fresh snapshot
    each). Its `insert … on conflict do nothing` cannot raise 23505. A concurrent creator's
    insert waits for the first to commit, then does nothing. The re-read that follows sees the
    committed row. The reminder upsert (`on conflict (user_id) do update`) is likewise safe.
  - With the profile in place, `GET /api/me` only reads (`accountOf`, `ensureProfile`, and
    `withUser`'s read-only repeatable read), and reads never wait on or fail from row locks.
  - In that test, the profile already exists: sign-up's after-commit hook is awaited inside the
    sign-up request, and `signedUp()` settles.
  - `ensureProfile` throws ("could not be made") only if the row is deleted between its insert and
    its re-read, which is account deletion, P3-T13's case.

Deviations:
- In production the stack is never written, even with no DSN. Architecture §10 says the stack
  goes to stderr "never in production", and an error's message or Drizzle's parameters can carry
  values; the interface contract alone would write it whenever the DSN is missing.

Open issues:
- Other failure logs still drop the cause: `after_response_failed` (`lib/after-response.ts`),
  `tool_failed` (`mcp/errors.ts`), `auth_task_failed`, `agent_task_failed`,
  `profile_create_failed`, and Better Auth's logger in `auth/auth.ts`, which receives the error but
  logs only `auth_error`. So a database failure inside Better Auth's session read reaches
  `internal()` as Better Auth's `APIError`, with no cause: such a 500 on `GET /api/me` would log
  `errorName: APIError` and no `pgCode`. Spreading `errorClass()` into those calls is a one-line
  change each, outside this brief's files.
- One mechanism that fits "once, in a full run, never alone" was not tested. Another process on
  the same Postgres cluster may set `netnet_app`'s password: every test file's bootstrap does, and
  so does `e2e.sh`. Every new pool connection after that fails with 28P01, and
  `GET /api/me`'s parallel reads after a `PATCH` are where the pool grows. Changing the role's
  password mid-run was not permitted in this session. A recurrence would now log
  `pgCode: 28P01`. CI runs each job against its own Postgres.
- Under heavy load, `test/mcp/lifecycle.test.ts`'s two rate-limit tests can exceed Vitest's 5 s
  default (above). This was not changed here.
