# P3-T19: Activity reads types by their labels, and dates as the screen does

Status: todo
Depends on: none
Parallel-safe: yes

## Goal

Activity names every type the way the rest of NetNet does, by its label in the person's current
pack, and the screen shows a value's date the way it shows every other date.

## Context

- Test report issue 1: a new Singapore account's log opens with 13 entries such as "Added type
  "car_loan"" and "Added type "listed"" (shown as "Investments" everywhere else). A move to GB
  adds "Added type "car_finance"". `summary()` in `apps/api/src/ledger/activity.ts` names a type
  by `customName ?? packTypeKey ?? universal`. The web's rename detail (`typeLabelOf` in
  `apps/web/src/routes/activity/activity.ts`) does the same.
- Core already names a type: `typeLabel(chain, type)` in `packages/core/src/pack-chain.ts` gives
  the person's own name, else the pack type's label, else the universal type's label. The export
  (`apps/api/src/ledger/export.ts`, through `s.chain()`), Home, Add and Archived use it. The web
  gets the chain from `usePackChain(snapshot.packRef)`.
- PRD J7: the log says what changed, readably. J2: labels follow the current pack, so after a
  country move an older entry reads with the new pack's label, as every other screen does. A
  pack type key the current chain lacks reads as its universal type's label, which `typeLabel`
  already does.
- Value entries read "Recorded a value for 2026-05-20". Every other date on the screen goes
  through `formatDate` (`apps/web/src/components/dates.ts`). The agent's `summary` keeps
  `YYYY-MM-DD`, like every date the MCP layer returns.
- **Unchanged:** the audit rows. `before` and `after` stay the entity as stored, and only the
  reading changes, so no migration is needed. Test report issue 4 (a country move that adds no
  type leaves no entry) is not part of this task.

## Interface contract

- `AuditEntry.summary` (REST `GET /api/activity` and MCP `list_activity`): a type entry names the
  type by `typeLabel(chain, snapshot)` over the person's current pack chain, read once per page:
  "Added type "Car loan"", "Removed type "Investments"", "Renamed type to "…"". A snapshot that
  cannot be read as a type still reads "a type" and never throws.
- The Activity screen: a type rename's detail reads both sides the same way ("“Car loan” → “My
  car”"). A value entry's date reads as `formatDate` gives it ("Recorded a value for May 20,
  2026" in an en-US browser). Every other entry shows `summary` as now.
- No change to the `AuditEntry` shape, the MCP output schema or the audit table.

## Report (filled by engineer)
Files changed: `apps/api/src/ledger/activity.ts` (a type entry's summary names the type by core's
`typeLabel` over `s.chain()`, read once for a page that has a type entry; `typeOf` reads a
snapshot as a type only when its `universal` is a universal type and its `packTypeKey` and
`customName` are text or null, absent reading as null, and anything else reads "a type"). Web:
`routes/activity/activity.ts` (`describeChange(entry, chain)` reads both sides of a type rename
with `typeLabel`, by the same snapshot rule; new `entrySummary(entry, locale?)` swaps the trailing
`YYYY-MM-DD` of a value entry's summary for `formatDate`'s reading and leaves every other summary
as it is), `routes/activity/Activity.tsx` (loads the log and the snapshot together, then the pack
chain through `usePackChain(snapshot.packRef)`, as Home and Archived do, with Waiting and the error
state for each). Tests: `apps/api/test/ledger/activity.test.ts`,
`apps/api/test/mcp/tools-reads.test.ts`, `routes/activity/activity.test.ts`,
`routes/activity/Activity.test.tsx`, `e2e/activity.spec.ts`.

Tests run / results: `pnpm lint`, `pnpm typecheck` green. `pnpm test`: 134 files / 1512 tests
pass. The API tests were written first and 7 of the 8 new ones failed before the change (the one
that passed, a type the person named, read by its name before too): every type a new qz ledger
starts with, by its label and never a key; a pack type added, renamed and removed; a type the
person made, through its rename and removal; a universal-only type removed and renamed, and a
snapshot without its empty keys; a pack key the chain lacks (qz's own type read through generic
alone, and a retired key through qz) in all three actions; eight unreadable snapshots in all three
actions read "a type"; after a move to another fictional country, older entries read with its
labels and the type it added by its pack's label; the chain read once for a page. The new
`list_activity` case (every type entry of a QZ account and a type the agent made, by label) failed
before the change too; the value summary it pins keeps `YYYY-MM-DD`. The web unit tests (a rename
of a pack type, a plain type, a named type and a missing key by label; unreadable sides give no
detail; a value's date in en-US and en-GB; other summaries untouched) failed first as well.
`pnpm test:int` (Postgres 16): 58 files / 746 tests pass. E2E (`e2e-run.sh 5441 3191
e2e/activity.spec.ts`): 10 passed at 390 and 1280 px, including a mocked log whose rename details
and value date read by the packs' labels and `formatDate`, and a real account against the
database: a new Singapore account's log names every type by its label (and the person's own type
by its name, and its value's date as "May 20, 2026"), then after a move to GB every entry reads
with the GB chain's labels and the added type by the GB pack's label.

Deviations: Activity now waits for the snapshot and the pack chain as well as the log, as the
other screens that name types do, so a failure to load either shows the screen's error state. A
snapshot whose `universal` is not a universal type reads "a type" even when it carries a name. The
E2E's real-account test runs only against the local app (`onlyAgainstTheLocalApp`), and the spec
now fixes its locale to en-US so the dates it checks are exact. No file outside the brief's list
was changed.

Open issues: none for this task. The web and the API each read a type snapshot by the same rule
(`typeOf`), because `apps/web` cannot import `apps/api` and the brief keeps `packages/core` out of
scope; one helper in core could serve both.
