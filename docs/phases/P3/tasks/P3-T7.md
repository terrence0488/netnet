# P3-T7: Periods — core, Ledger and the agent tool

Status: done
Depends on: P3-T2, P3-T4, P3-T6 (ordering only — Insights is built last in the phase so a slip shows against the phase rather than eating the trust work, PRD §4.1; no technical dependency)
Parallel-safe: yes

## Goal

One deterministic period engine: calendar periods derived from value dates with
carried-vs-observed marking, drivers ranked by contribution, and filters and
exclusions — used by the web from the snapshot and by the agent through one
tool.

## Context

- PRD J11 is the contract; architecture §7.9 (`core.periods`) and §7.3
  (`Ledger.periods`), §7.4 (`get_period_changes`) are the spec.
- Periods derive from **value dates**, never entry time. A holding with no
  value inside a period carries its last known value before the period end,
  marked carried rather than observed. Every figure uses each entry's recorded
  default-currency conversion, so later FX moves never distort a closed period.
- The web computes periods locally: the snapshot already carries every value,
  which makes filters and Insights instant with the same `core` code
  (architecture §7.2). There is **no new REST endpoint** in this task.
- `core` stays pure (CONVENTIONS §3, N11): `today` passed in, no I/O, no
  randomness. Money in minor units, conversion through `core.convert` only.

## Interface contract

```ts
// packages/core
periods(values, holdings, view: 'monthly'|'quarterly'|'yearly', filter, exclusions): Period[];
// Period: { start, end, endValue, change, changePct, carried: boolean,
//           drivers: [{ holdingId, name, contribution }] } — drivers ranked by
//           contribution in the default currency, minor units; exclusions drop
//           holdings/types/tags from the figures without touching Home totals.

Ledger.periods(q: PeriodQuery): Promise<PeriodTable>;
```

- MCP `get_period_changes {view, periods?≤24, drivers?}` (read) → period-end
  value, change, % change, top contributors per period; paged over at most 24
  periods. Carries `outcome` and `latency_ms` like the other tools.
- Insights filters and exclusions persist through the existing
  `PATCH /api/prefs` under the keys `insightsFilter` and `insightsExclusions`
  (additive detail under plan rule 4; list in the report). Home's filter keys
  are untouched: the two filters are separate.
- Filters recompute every figure over the filtered set; exclusions drop a
  holding, type or tag from Insights figures only.

Deviations (all additive details under plan rule 4):
- The `insightsExclusions` pref key, and the §7.2 prefs-row key list, as the
  brief instructs. Shape: `{holdingIds?, typeIds?, tagIds?}` — the PRD's
  "a holding, type or tag", kept apart from `insightsFilter` so the Insights
  screen (P3-T9) can keep the Don't Show list separate. Scrubbed on
  delete/merge like the filters.
- `core.periods` takes `today` (the brief's "`core` stays pure: today passed
  in"): periods run from the earliest value's bucket to today's, the current
  one still open with `end` = today. No §7.4/§7.3 change: the tool and
  `Ledger.periods` take no date; the server supplies it. The §7.9 one-liner is
  schematic (as with `series`' `groupBy`); no other §7 change was needed.
- `core.periods` returns oldest-first (like `series`); `Ledger.periods` and the
  tool return newest-first per the PRD, taking the newest `periods`.
- First period: `change` = `endValue` (from 0), `changePct` = null (the
  `baselineChange` base-0 rule). `change`/`changePct` otherwise follow
  `baselineChange` exactly, unrounded.
- `drivers` holds only nonzero contributions, ranked by signed contribution
  descending, ties by name then id. A flat period reports `drivers: []`.
- Tool/Ledger defaults: 12 periods, 5 drivers; caps 24 (per §7.4) and 25.
- `lifecycle`/`protocol` tests now expect seventeen tools (were sixteen);
  `server.ts`'s "sixteen tools" comment is count-free. `PREF_KEYS` test covers
  the five keys.
