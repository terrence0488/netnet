# P3-T12: The default-currency change — one entry, a person's own rates kept

Status: todo
Depends on: P3-T11
Parallel-safe: yes

## Goal

Changing the default currency is one entry in Activity, however many values it re-derives. A rate
the person or their agent gave stays theirs through any number of changes, so a round trip lands
back on their own figures exactly.

## Context

- Test report issue 1, without the undo half that P3-T11 removes: an SGD ledger switched to USD
  writes one "Changed the default currency" entry plus one entry per value, each reading
  "$23,700 → $23,700 SGD". A real account would get hundreds of rows. Feedback item 3 decides
  that the change shows as **one entry**.
- Test report issue 6: a USD holding entered at the person's rate of 1.35 in an SGD ledger,
  switched to USD and back, comes back at the ECB's 1.30 (`fx_source` user → ecb), and S$135
  becomes S$130 in history and in every period. The cause is in
  `apps/api/src/ledger/currency.ts` → `rederive`: a value already in the new default currency
  becomes `same` with rate 1, and the person's rate is gone. Carrying a given rate from one
  default to the next also compounds rounding over several changes.
- Architecture §6.3 (the value's new `given_rate`, `given_rate_into` and `given_rate_by`), §6.6
  (the rule below), §6.8 (one audit row for a re-derivation), §7.2 (the export's two new CSV
  columns). P3-T3's report describes the code as it stands.
- A given rate's date is the value's own date (`prepareValue` in `ledger/money.ts`).
- The backfill reads current values only. A rate already lost to an earlier round trip is not
  recovered: the person enters it again. Production holds only the Founder's and the probe's
  accounts.
- Earlier per-value re-derivation entries in production stay as they are.

## Interface contract

- **Migration:** `ledger.value` gains `given_rate numeric`, `given_rate_into char(3)` and
  `given_rate_by` (`user`/`agent`). All three are null or all three set (a check constraint).
  Backfill: each value with `fx_source` `user` or `agent` gets `given_rate = fx_rate`,
  `given_rate_into = base_currency`, `given_rate_by = fx_source`.
- **Value writes:** recording or editing a value with a rate sets the three columns (`into` = the
  default currency at the time, `by` = the actor). An edit to the amount or date keeps them. A
  currency change without a new rate clears them.
- **`changeBaseCurrency(ccy)`:** for each value, in the new default currency `to`:
  - value currency = `to` → `base_minor = amount_minor`, rate 1, `fx_source: same`; the given rate
    is kept, unused;
  - given rate into `to` → that rate, at the value's date, `fx_source = given_rate_by`;
  - given rate into another currency → the given rate × the stored cross rate (`given_rate_into` →
    `to`) at the value's date, `fx_source = given_rate_by`;
  - no given rate → the stored published rate from the value's currency into `to`, as now.

  One write, one audit row: entity `ledger`, `{baseCurrency: from}` → `{baseCurrency: to,
  valuesRederived: n}`, with no row per value. `data_version + 1`. A missing rate or an
  out-of-range result still fails the whole change and names the value.
- **Activity:** the entry reads as one row, "Changed the default currency SGD → USD", with the
  number of values re-derived (copy from the design system's voice).
- **Export:** JSON values carry `givenRate` and `givenRateInto` (null when none). The CSV header
  ends `…,tags,given_rate,given_rate_into` (architecture §7.2).
- Where a value's rate is already readable by the agent (`get_holding`), the given rate rides
  with it. That field is implied by the architecture: list it in the report.
